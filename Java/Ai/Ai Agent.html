AI Agent

AI Agent 是什么

先看一个常见需求：用户说“帮我查一下最近一笔订单，如果已经发货，告诉我预计什么时候送达”。系统需要识别用户意图，确认用户身份，找到订单，查询物流，并根据结果组织回答；如果没有订单、没有权限或物流服务暂时不可用，还要知道如何处理。

如果步骤和分支都能提前确定，程序可以按固定流程执行；如果下一步取决于上一步的结果，就需要一个能够观察结果并动态选择行动的执行系统。AI Agent（人工智能代理或智能体）就是围绕这类目标运行的软件系统：它接收目标和约束，读取任务状态，选择下一步行动，通过模型、工具、检索和记忆推进任务，并在完成、取消、超时或触发安全条件时停止。

可以把它概括为：

Agent = 目标 + 状态 + 决策 + 行动 + 反馈 + 停止控制

这里的“自主”是在给定边界内选择下一步。模型通常负责理解信息、判断选项和提出行动意图；应用程序负责身份认证、权限校验、参数验证、工具执行、预算控制和结果交付。模型说“请查询订单”，不等于订单已经被查询。

一次订单查询可以抽象为：

用户目标
  → 理解目标和约束
  → 读取身份、任务状态和可用能力
  → 选择直接回答、询问用户或调用工具
  → 执行行动并获得观察结果
  → 根据结果继续、调整、交付或停止

普通 LLM（Large Language Model，大语言模型）调用通常是“输入提示，生成一次回答”；调用方在请求前已经决定了步骤。Agent 的区别在于，它可以根据中间结果继续查询、改用其他工具、询问用户或结束任务。

对比项普通 LLM 调用AI Agent
任务范围生成一次回答或内容持续推进一个任务目标
决策次数通常一次可以进行多轮决策
信息来源当前请求和已提供的上下文状态、记忆、检索结果和工具结果
行动能力主要输出文本可以选择工具或外部服务
执行路径调用方预先确定可根据观察结果调整
结束方式输出完成后结束满足完成、取消、超时、预算或安全条件后结束

“把订单说明改写得更礼貌”通常一次 LLM 调用就够了；“查询用户有权访问的订单，必要时查物流并给出有依据的结论”则需要状态、工具和多步判断，更适合采用 Agent。

Agent、AIGC 与 AGI 的区别

这三个词经常一起出现，但它们回答的是三个不同的问题：

概念全称和中文含义主要回答的问题典型输入、过程和输出不负责什么
AIGCAI Generated Content，人工智能生成内容AI 生成了什么内容？输入文字或图片要求 → 模型生成或修改内容 → 输出文章、图片、音频或代码不代表系统会自己规划任务、调用业务工具或保证事实正确
AgentAI Agent，人工智能代理或智能体AI 如何围绕目标采取行动？输入目标和约束 → 读取状态、选择行动、调用工具并检查结果 → 输出完成结果或明确的失败原因不代表模型拥有真实权限，也不代表一定具备通用智能
AGIArtificial General Intelligence，通用人工智能AI 是否能跨领域学习和完成广泛任务？输入陌生领域目标 → 理解新知识并迁移能力 → 输出多个领域中都可靠的完成结果不是一个已经由普通 Agent 产品自动实现的能力

可以用同一个“海报任务”区分它们：

  • AIGC：用户给出主题和文案，模型生成一张海报。重点是内容生成质量。
  • Agent：系统先理解需求，再收集素材、检查品牌规范、调用设计工具、让用户确认并交付文件。重点是围绕目标组织多个步骤。
  • AGI：系统面对从未见过的行业和工具，也能自己学习规则并稳定完成类似任务。重点是跨领域的通用能力。

因此，AIGC 是 Agent 可以使用的一种内容生成能力；Agent 是一种系统组织方式；AGI 是关于通用能力的研究目标。一个能生成内容或调用工具的产品，不能仅凭这一点称为 AGI。

Workflow 与 Agent 如何分工

Workflow（工作流）是由程序预先定义的任务流程。它把步骤、输入、输出、顺序、分支和失败处理写进代码或配置中，运行时按照既定规则执行。它解决的是“怎样稳定地重复执行一条已知流程”。

以订单查询为例，一个固定 Workflow 可以是：

输入用户身份
  → 校验登录状态
  → 查询最近订单
  → 查询物流状态
  → 按订单状态生成回答

每个步骤都有明确的输入和输出：登录校验输出可访问的用户身份；订单查询输出订单编号或空结果；物流查询输出状态和时间；最后一步只负责组织已经取得的数据。程序还可以规定查询超时重试两次、没有订单就直接返回、物流已签收就不再查询预计送达时间。某个步骤可以调用 LLM 生成自然语言，但步骤顺序和分支仍由程序控制。

Workflow 适合审批、订单处理、固定报表、数据同步等规则稳定的任务。它的优点是路径清楚、结果容易测试、失败容易重放和审计；局限是面对开放式目标或未预料的中间结果时，预先写好的路径可能覆盖不全。

Agent 解决的是另一类问题：下一步行动不能完全提前写死，需要根据当前观察结果动态选择。例如，订单查询工具返回“订单已取消”，Agent 就不必再查配送时间；返回“订单号缺失”，Agent 应先询问用户；返回物流服务不可用，应用则需要决定重试、切换服务或向用户说明暂时无法查询。

对比项WorkflowAgent
下一步由谁决定程序和预先定义的规则模型根据状态和观察结果提出选择
路径是否固定大部分路径在运行前确定路径可以在运行时变化
适合的任务确定性流程和高审计要求场景开放式目标和多工具协作场景
主要优势稳定、可测试、可预测灵活、能处理未预料结果
主要风险规则遗漏、流程僵化循环失控、成本上升、行为难预测
重点控制状态机、事务、重试和审计决策循环、工具边界、预算和停止条件

实际系统可以把两者组合起来：外层 Workflow 固定登录、权限、人工审批和结果交付；中间需要动态判断的部分交给 Agent。能用固定流程稳定解决的部分，应保持固定，只有确实需要根据中间结果选择下一步时才引入 Agent。

Agent Loop：Agent 如何完成任务

Agent Loop（Agent 循环）是 Agent 反复执行“读取状态 → 决策 → 行动 → 观察 → 判断是否结束”的运行机制。它把一次模型调用变成了可控制的任务过程。循环的关键不是让模型无限思考，而是让每一轮都有明确输入、行动和停止条件。

下面用订单查询助手表示完整链路：

flowchart TD
    INPUT[用户目标] --> STATE[读取任务状态]
    STATE --> DECIDE[模型选择下一步]
    DECIDE --> ACTION{行动类型}
    ACTION -->|缺少信息| ASK[询问用户]
    ACTION -->|直接回答| ANSWER[生成回答]
    ACTION -->|调用工具| VALIDATE[校验参数和权限]
    VALIDATE -->|拒绝| DENY[返回拒绝或错误]
    VALIDATE -->|允许| TOOL[执行查询或业务工具]
    TOOL --> OBSERVE[记录工具结果]
    OBSERVE --> CHECK{完成或需要停止?}
    CHECK -->|继续| STATE
    CHECK -->|是| ANSWER

每轮通常包含以下步骤：

  1. 读取状态：加载目标、已确认参数、对话摘要、工具结果、权限、预算和取消信号。
  2. 模型决策：选择直接回答、询问用户、调用工具、检索资料或调整计划。模型输出的是行动意图，不是已经执行的事实。
  3. 应用校验和执行：检查工具名称、参数结构、用户权限和风险等级，通过后才真正执行工具；高风险行动可能需要人工确认。
  4. 写回观察结果：保存成功结果、错误码、来源、耗时和状态变化，供下一轮使用。
  5. 检查停止条件：判断任务是否完成，或是否因为取消、超时、预算耗尽、连续失败、重复调用或需要人工确认而停止。

以“最近一笔订单”为例：第一轮根据用户身份查询订单；如果没有订单编号但工具支持按时间查询，就直接按时间查询，否则先询问用户；拿到订单号后查询物流；物流服务超时时，由应用根据错误类型决定是否重试；结果足够回答时，循环结束。每次工具调用都应有可记录的结果，模型不能用一句“我已经查过了”代替真实查询。

生产系统至少应设置最大迭代次数、总超时时间、Token 或费用预算、取消机制、重复调用检测和失败恢复策略。重试还要区分可重试错误和不可重试错误，避免网络故障重试变成重复扣款。付款、删除、发布和生产数据修改等操作，要在工具执行前增加权限检查、幂等控制和人工确认。

Agent 的组成

一个可运行的 Agent 通常由以下部分协同构成：

用户目标
   ↓
应用状态 ←→ Agent Loop ←→ 模型
   ↓              ↓
记忆、检索       工具和外部服务
   └────── 运行控制与观测 ──────┘
  1. 模型（Model）：理解输入、提取信息、判断下一步并生成结果。大语言模型适合处理开放式语言，也可以搭配分类模型、向量嵌入模型（Embedding）或其他专用模型。
  2. 状态（State）：保存本次任务的目标、已确认参数、计划、对话摘要、工具结果和当前状态，回答“这次任务进行到哪里了”。任务结束后，状态通常可以归档或删除。
  3. 记忆（Memory）：保存经过筛选、允许长期使用的信息，例如用户偏好或已确认的业务事实。记忆需要来源、时间和隐私策略，不应无条件保存所有对话。
  4. 检索（Retrieval）：从知识库或外部资料中查找与当前问题相关的信息，并把经过权限过滤的结果放入上下文。检索提供资料，不等于资料一定正确。
  5. 决策循环（Agent Loop）：根据状态和观察结果选择继续、调整、询问、交付或停止。
  6. 工具（Tools）：连接搜索、计算、数据库和业务 API 等外部能力。工具执行前必须经过参数、权限、幂等和风险校验，执行后应返回结构化结果和错误信息。
  7. 运行控制（Runtime）：负责调度、超时、重试、并发、预算、取消、人工确认、日志和停止原因记录。
  8. 观测与交付：记录行动、工具结果、耗时、成本和错误，把经过验证的结果交给用户或下游系统。

这些部分的职责不能混在一起：模型负责提出判断，应用负责执行和约束；状态记录当前任务，记忆服务于跨任务复用；检索提供候选资料，工具执行真实操作；运行控制负责让任务可暂停、可取消、可审计。

什么时候需要 Agent

可以按下面的顺序判断：

  • 输入和输出清楚，只需生成一次：使用普通 LLM 调用；
  • 步骤、分支和失败处理都能提前确定：优先使用 Workflow；
  • 需要实时资料或访问外部系统：增加检索或工具，不一定需要 Agent；
  • 下一步必须根据中间结果动态选择，且任务有明确完成目标：考虑 Agent Loop；
  • 涉及付款、删除、发布或生产数据修改：无论采用哪种方式，都要由应用执行权限控制、风险校验、幂等控制和人工确认。

引入 Agent 前，可以先问：任务目标是否清楚？下一步是否真的无法提前写死？动态决策带来的收益是否值得承担额外的延迟、成本和调试复杂度？如果固定流程已经能稳定完成任务，就不必增加 Agent 层。

Prompt 工程

前面介绍了 Agent 会根据任务状态选择下一步，但模型并不会自动知道“要完成什么、可以做什么、什么时候应该停”。应用需要把这些内容写进发送给模型的 Prompt（提示词）中。

Prompt 可以先理解成一份写给模型的任务说明书。它告诉模型任务目标、已知信息、行为规则和回答格式。Prompt 工程（Prompt Engineering）就是不断改进这份说明，让模型在正常输入、缺少信息和异常情况下都能按预期工作。

Prompt 是什么

还是以订单查询助手为例。用户说“帮我查订单”，这句话至少缺少订单编号、查询范围和返回内容。模型如果直接回答，可能会猜测订单状态；如果应用希望它先追问，就必须明确写出来。

最简单的 Prompt 可能只有一句话：

帮我查订单。

它的问题不是语气不够好，而是任务没有定义清楚。一个更可执行的版本是：

你是订单查询助手。
目标：查询当前用户有权访问的订单状态。
规则：缺少订单编号时先询问；不能猜测订单状态；不要修改订单。
输出：订单编号、当前状态、更新时间。

这段文字已经包含了角色、目标、规则和输出要求。对于 Agent，还需要说明工具什么时候使用、工具失败时怎么办：

职责：查询当前用户有权访问的订单状态，不处理订单修改。

执行规则：
1. 缺少订单编号时，先询问编号，不自行猜测。
2. 编号齐全时，调用已注册的 get_order 工具。
3. 工具成功时，只使用工具返回的数据回答。
4. 未找到、无权限或工具超时时，说明查询无法完成。

回答格式：订单编号、当前状态、更新时间。

Prompt 只描述模型应如何理解任务和提出行动意图。它不能代替应用程序完成身份认证、权限校验、参数验证、工具执行和预算控制。模型说“请查询订单”，不等于订单已经被查询。

怎样组织一份 Prompt

面向初学者，可以按下面的顺序写：

角色/职责
→ 任务目标
→ 已知信息
→ 行为规则
→ 工具使用规则
→ 输出格式
→ 失败和拒答条件

每一部分解决一个问题：

  1. 角色和职责：模型在当前任务中负责什么，不负责什么；
  2. 目标：什么结果才算完成；
  3. 已知信息：当前用户、任务状态、已确认参数和可信资料；
  4. 行为规则：何时直接回答、何时追问、何时调用工具；
  5. 工具规则：工具解决什么问题，参数缺失或调用失败时怎么办；
  6. 输出格式：回答给用户看，还是返回给程序继续处理；
  7. 失败条件：没有证据、没有权限或风险过高时如何停止。

不同来源的内容要分开标记，避免把用户输入或外部资料误当成系统规则：

<system_rules>
你只能查询当前用户有权访问的订单。
</system_rules>

<user_request>
{用户原始问题}
</user_request>

<retrieved_context>
{检索到的资料}
</retrieved_context>

这些标签只是文字分隔符，不会自动提供安全能力。应用仍要在填入内容前完成权限过滤、敏感信息处理和长度限制。用户输入、检索文档和工具结果都可能包含提示词注入，不能直接覆盖系统规则。

从需求到可执行的 Prompt

角色名称只能提供背景，具体规则才能帮助模型做出判断。可以用订单查询助手逐步补全需求：

阶段提示内容解决的问题
只给需求帮我查订单不知道查询什么、从哪里查、返回什么
明确目标查询用户提供的订单编号，返回最新状态明确任务目标
指定来源状态必须来自订单查询工具防止模型凭记忆猜测
补充分支没有编号就追问，查不到就说明未找到处理缺失信息和空结果
定义交付输出编号、状态、更新时间明确完成标准

常用的提示方式可以先这样理解：

  • 零样本提示（Zero-shot）：只写任务和规则，不提供示例，适合简单且边界清楚的任务；
  • 少样本提示（Few-shot）：给出几组“输入 → 期望输出”，帮助模型理解容易混淆的边界；
  • 分步任务说明：把复杂目标写成理解、判断、行动和验证几个阶段，但不要求模型暴露完整内部思维链；
  • 结构化输出：要求返回固定字段，方便程序读取和校验，下一章会详细说明；
  • 工具使用规则：说明缺少参数时先询问，哪些错误可以重试，哪些情况必须停止。

Few-shot 适合解释“什么时候应该追问”。例如：

输入：查一下 A1001 的订单状态。
输出：{"order_id":"A1001","missing_fields":[]}

输入：帮我看看订单到哪了。
输出：{"order_id":null,"missing_fields":["order_id"]}

输入：我的用户编号是 U88，帮我查订单。
输出：{"order_id":null,"missing_fields":["order_id"]}

第三个示例说明用户编号不能当成订单编号。示例应覆盖正常输入、缺少信息、混淆字段和边界情况；只提供成功案例，模型可能学不到何时拒绝或追问。示例中的 JSON 仍需要程序校验，是否保留示例应通过固定评测集判断，而不是凭一次观察决定。

模板变量和消息角色

实际应用不会每次手写完整 Prompt，而是使用模板。模板中的 {user_request}、{order_result} 等是变量，分别代表用户问题和工具结果。应用应为每个变量定义来源、类型、允许为空的情况、长度上限和脱敏规则，发送前检查是否存在未替换的占位符。

支持消息角色的模型 API 通常会区分系统或开发者消息、用户消息和工具消息。应用规则放在高优先级的系统或开发者消息中，用户问题放在用户消息中，工具结果放在工具消息中；具体角色名称和优先级以所用 API 为准。不要把所有文本简单拼成一条消息，也不要把用户填写的字符串当成系统规则。

规则之间要保持一致。例如“无论如何都给出答案”与“没有证据时说明无法回答”存在冲突；“只输出 JSON”与“先用自然语言解释”也存在冲突。遇到冲突时，先修改模板，再评估模型表现。

模板还要区分事实和待验证信息：工具结果应带来源、时间和状态；检索资料应标记为参考内容；用户输入只能表达需求，不能自动改变权限或系统规则。

Prompt 缓存与持续改进

当多次请求使用相同的系统规则、工具定义和示例时，模型服务可能复用已经处理过的输入前缀，这叫 Prompt Caching（提示词缓存）。它主要减少重复输入的处理开销，具体是否降低费用、降低多少费用，取决于模型服务的计费方式。

Prompt 缓存不是响应缓存：它复用输入处理结果，模型仍要结合本次问题生成回答；它也不是长期记忆，缓存服务性能，记忆保存和检索跨会话信息。

机制复用什么本次是否仍生成答案主要用途
Prompt 缓存已处理的输入前缀是减少重复输入处理
应用响应缓存之前生成的完整答案命中时通常直接返回直接复用确定结果
长期记忆用户偏好、历史结论等信息通常作为新请求的背景跨会话保留信息

稳定前缀与动态内容

对于支持前缀缓存的服务，缓存通常从输入开头匹配一段连续内容。可以按下面的顺序组织请求：

稳定部分：工具定义、系统规则、固定示例
    ↓
可复用部分：版本不变的资料、已确认的对话历史
    ↓
动态部分：当前问题、本轮检索结果、时间等变量

例如两个订单查询请求只有订单编号不同：

请求 A：[固定规则 + 工具定义 + 示例] + 查询 A1001
请求 B：[固定规则 + 工具定义 + 示例] + 查询 A1002
         └──── 可复用前缀 ────┘

首次请求可能需要建立缓存，后续请求才可能读取缓存。如果把不断变化的时间戳、随机 ID 或本轮问题放在最前面，即使后面的规则完全相同，公共前缀也可能很短。为了减少非必要变化，应固定工具列表顺序、模板格式、字段顺序和示例顺序，避免每次随机排序。

缓存优化不能改变权限边界。权限不同的用户必须分别组装允许使用的工具和资料；不能为了提高命中率注入无权访问的内容，也不能保留已经过期的业务资料。稳定前缀的版本更新后，旧缓存是否还能使用由服务决定，应用应把模板版本纳入日志。

不同服务对启用方式、最小长度、有效期、缓存淘汰和计费规则有不同要求。例如 Claude 提供自动缓存配置和显式缓存断点，相关使用量可以从响应中读取。具体配置应按模型和部署平台核对，不应把一套 API 参数直接复制到所有服务。Claude 官方 Prompt 缓存文档

缓存命中率和 Token 复用率

“缓存命中率”至少有两种常见统计口径。应用应先把供应商响应中的字段统一为“本次总输入 Token”和“缓存读取 Token”，再计算指标：

请求命中率 = 缓存读取 Token 大于 0 的请求数 / 总请求数
Token 复用率 = 缓存读取 Token 总和 / 总输入 Token 总和

请求命中率回答“多少请求读取过缓存”；Token 复用率回答“全部输入中有多少 Token 被复用”。两者不能互相替代：一条很短的请求只读取了少量 Token，也会被算作请求命中。

例如统计 10 次请求，每次总输入为 2,000 Token。第一次请求建立缓存，后续 9 次各读取 1,500 Token：

请求命中率 = 9 / 10 = 90%
Token 复用率 = 9 × 1,500 / (10 × 2,000) = 67.5%

汇总多个请求时，应先累加分子和分母，再计算比例。直接平均每次请求的复用率，会让很短的请求和很长的请求获得相同权重，结果可能偏离实际 Token 使用情况。

供应商字段和统计陷阱

以 Claude 的使用量字段为例：

字段含义是否属于本次总输入
input_tokens未从缓存读取、也未用于建立缓存的输入 Token是
cache_creation_input_tokens本次用于写入缓存的输入 Token是
cache_read_input_tokens本次从缓存读取的输入 Token是

在这种口径下：

总输入 Token = input_tokens
             + cache_creation_input_tokens
             + cache_read_input_tokens

其他服务可能把缓存 Token 作为总输入的子字段返回，也可能直接返回已经汇总的总数，不能看到字段名称相似就重复相加。写入缓存不等于读取命中：首次请求可能只有缓存写入，没有缓存读取，因此应分别记录创建量和读取量。Claude 官方字段说明

对于不满足最小长度或不支持缓存的请求，可以额外统计“符合缓存条件的请求命中率”，但必须明确筛选条件，并同时保留总体指标，否则容易因为只统计有利样本而高估效果。

缓存未命中如何排查

现象可能原因检查方向
一直没有缓存读取未启用、模型不支持、前缀过短或请求间隔超过有效期检查模型、配置、最小长度和有效期
刚修改模板后命中下降稳定前缀内容或顺序发生变化对比模板、工具定义和字段顺序版本
连续调用命中，间隔后失效缓存过期或被服务淘汰核对有效期、流量和淘汰规则
相同任务偶尔不命中路由、区域、模型或内容顺序发生变化对比实际发送内容和请求路由

排查时应记录实际发送的 Prompt 版本、模型、区域、工具顺序、稳定前缀长度、缓存创建量和缓存读取量。只比较“看起来相同的模板”不够，因为一个空格、字段顺序或动态变量位置变化，都可能影响前缀匹配。

性能和收益评估

可以先用两次内容完全相同的稳定前缀请求做最小验证：第一次观察缓存创建或输入处理情况，第二次观察是否出现缓存读取。这个实验只能确认配置可能生效，不能代表真实流量下的收益。

生产评估至少同时观察：

  • Token：输入总量、缓存写入量、缓存读取量和输出量；
  • 延迟：首 Token 延迟（TTFT）、总响应时间和工具等待时间；
  • 费用：缓存读取、缓存写入和普通输入的实际单价；
  • 质量：任务成功率、工具选择正确率、结构化输出正确率和拒答准确率；
  • 稳定性：不同用户、不同路由和不同时间段的命中差异。

读取缓存仍可能计费，输出生成也有成本，因此 Token 复用率不等于费用降低比例。为了凑够最小缓存长度而添加无关示例，可能增加延迟和干扰模型判断；只有当节省的处理成本和延迟收益能够通过实际指标验证时，缓存优化才有意义。

生产环境还应把 Prompt 当作可版本管理的配置。每次修改记录 Prompt 版本、适用模型、变量、工具定义、稳定前缀组成、缓存指标和评测结果，并使用固定问题集回归测试：正常请求、缺失参数、空结果、工具失败、权限拒绝、提示词注入和资料不足都要覆盖。只有目标指标改善且成本与风险可接受时，才推广新版本。

结构化输出与结果验证

模型习惯用自然语言回答，但程序需要读取明确的状态、字段和动作。比如订单查询助手需要知道当前是“查到了订单”“缺少订单编号”还是“物流服务失败”。如果只让模型返回一段话，程序就必须猜测这段话的含义，容易在边界情况下出错。

结构化输出就是让模型按照约定格式返回数据，例如 JSON（用字段和键值表示数据的文本格式）。应用先解析这些数据，再做校验，最后决定继续询问、调用工具、展示结果或停止。

结构化输出解决的是“结果怎样被程序读取”，不负责证明内容一定真实，也不负责授予权限。合法 JSON 可能包含错误的订单状态，应用仍要以真实工具、权限规则和业务数据为准。

从自然语言到固定字段

用户缺少订单编号时，可以让模型返回：

{
  "status": "need_clarification",
  "missing_fields": ["order_id"],
  "message": "请提供订单编号"
}

查询成功时，可以返回：

{
  "status": "success",
  "order": {
    "order_id": "A1001",
    "state": "shipped",
    "updated_at": "2026-10-09T10:30:00+08:00"
  },
  "next_action": "query_delivery"
}

物流服务暂时不可用时，可以返回：

{
  "status": "tool_error",
  "error_code": "delivery_service_unavailable",
  "retryable": true,
  "message": "暂时无法查询物流，请稍后重试"
}

应用可以根据 status 和 retryable 决定下一步。字段名称和状态值应保持稳定，避免同一含义在不同请求中交替使用 success、done 和 completed。

如何设计结构

先确定应用真正需要哪些字段，再决定格式。初学者可以先记住以下原则：

  • 状态字段：用少量固定值表示成功、需要补充信息、未找到、拒答或工具失败；
  • 业务数据：只返回后续程序确实需要的字段；
  • 下一步动作：说明应用应该继续询问、调用哪个已注册工具或结束任务；
  • 错误信息：用稳定的错误码供程序判断，用 message 保存给用户看的文字；
  • 来源和时间：需要引用资料或工具结果时记录来源和数据时间；
  • 空值规则：明确字段是省略、返回 null，还是返回空数组。

当字段较多时，可以使用 JSON Schema 描述结构。Schema 可以理解为“数据格式的检查清单”，用于规定字段、类型和允许的值：

{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "status": {
      "type": "string",
      "enum": ["success", "need_clarification", "not_found", "tool_error"]
    },
    "order_id": {"type": ["string", "null"]},
    "missing_fields": {
      "type": "array",
      "items": {"type": "string"}
    },
    "retryable": {"type": "boolean"},
    "message": {"type": "string"}
  },
  "required": ["status", "order_id", "missing_fields", "retryable", "message"]
}

Schema 能检查字段是否存在、类型是否正确和枚举值是否有效，但不能检查订单是否属于当前用户、物流时间是否合理，也不能替代数据库和业务规则。不同模型服务对 JSON 模式和 Schema 关键字的支持不同，使用前应查看对应文档。

应用怎样验证结果

结构化输出不是模型返回后就可以直接执行。应用应按从简单到严格的顺序检查：

flowchart TD
    MODEL[模型输出] --> PARSE[解析格式]
    PARSE -->|失败| REPAIR[有限修复或重试]
    PARSE -->|成功| SCHEMA[Schema 校验]
    SCHEMA -->|失败| REPAIR
    SCHEMA -->|成功| VALUE[字段和枚举校验]
    VALUE -->|失败| STOP[返回明确错误]
    VALUE -->|成功| BUSINESS[业务和权限校验]
    BUSINESS -->|拒绝| STOP
    BUSINESS -->|通过| LOOP[交给循环或执行层]
  1. 格式解析：确认内容是完整 JSON，处理代码围栏、额外说明和截断输出；
  2. Schema 校验：检查必填字段、类型、数组元素和额外字段；
  3. 值校验：检查枚举、长度、时间格式、数值范围和字段之间的关系，例如 status=success 时必须有订单数据；
  4. 业务校验：确认订单属于当前用户，状态来自可信工具，下一步动作属于已注册能力；
  5. 交接或停止：校验通过后交给 Agent Loop 或业务服务，失败时进入修复、重试、询问或人工处理。

前两步主要检查“格式对不对”，后两步检查“内容能不能用”。业务和权限校验必须由应用完成，不能只写在 Prompt 里。

失败处理和边界

失败类型示例处理方式
格式错误JSON 少了引号或被截断请求模型只修复格式，或有限重试
字段缺失没有返回 status记录校验错误，必要时重新生成
类型错误retryable 返回字符串重新请求或转为失败状态，不能隐式猜测
枚举错误返回 done，但只允许 success修正 Schema 或要求使用已注册枚举
业务错误返回了其他用户的订单号直接拒绝，不能靠重试绕过权限
事实错误JSON 合法但物流状态与工具结果不符以可信工具和业务数据为准

重试要有上限，并区分“可以重新生成格式”和“不能通过重试解决”的错误。格式错误可以尝试一次或少量修复；权限拒绝、业务数据不一致和高风险动作不应重复执行。连续失败时，应向用户说明无法完成、请求补充信息或转人工，不能把原始字符串直接当成可靠结果。

校验失败时可以记录 Prompt 版本、模型版本、原始输出摘要、失败层级和错误原因，便于判断问题来自模型、Schema 还是业务数据。原始输出可能包含敏感信息，日志需要脱敏并限制访问。

结构化输出也不等于要求模型暴露完整内部思维过程。应用只需要状态、字段、行动建议和必要的结果解释；调试时记录校验失败原因和工具调用摘要即可。

Tool 工具调用

模型擅长理解文字和生成内容，但它不知道数据库里的实时订单，也不能凭空发送邮件或修改业务数据。Tool（工具）就是应用提供给 Agent 的外部能力，让模型可以提出“查询订单”“搜索资料”或“计算数据”等行动请求，再由应用决定是否真的执行。

以“查询订单 A1001”为例：模型只能判断应该查询订单，应用才有权限调用订单服务。一次完整的工具调用包含四件事：

  1. 工具定义：告诉模型工具叫什么、适合解决什么问题、需要哪些参数；
  2. 调用意图：模型选择工具并生成参数，表达“想做什么”；
  3. 应用执行：应用验证参数、权限和风险后，调用真实 API 或数据库；
  4. 工具结果：应用把成功数据或可处理的错误写回上下文，模型再决定回答或继续行动。

工具不是 Prompt 中的一段说明，也不是模型自动拥有的函数。模型只提出调用意图，真正访问数据和修改业务的始终是应用程序。

一次工具调用的完整流程

下面的流程展示模型、应用和工具各自负责什么：

sequenceDiagram
    participant U as 用户
    participant A as 应用
    participant M as 模型
    participant T as 工具
    U->>A: 提交请求
    A->>M: 发送消息和工具定义
    M-->>A: 返回工具调用意图
    A->>A: 校验参数、权限和风险
    A->>T: 执行工具
    T-->>A: 返回结构化结果
    A->>M: 写回工具结果
    M-->>A: 继续调用或生成答案
    A-->>U: 返回结果

按顺序看：

  1. 应用把当前任务和允许使用的工具定义发送给模型；
  2. 模型根据用户问题选择工具，并生成结构化参数；
  3. 应用解析调用请求，检查参数、用户身份、租户范围和风险等级；
  4. 对付款、删除、发布等高风险操作，应用在执行前请求用户确认；
  5. 应用调用真实服务，把成功数据或稳定的错误结果写回上下文；
  6. 模型根据结果生成回答、询问补充信息、改用其他工具或结束任务。

因此，工具调用的准确理解是：“模型提出调用意图，应用负责判断和执行”，而不是“模型直接执行函数”。

工具定义与参数

工具定义是给模型看的说明，同时也是应用解析调用请求的约定。一个查询订单的工具可以写成：

{
  "name": "get_order",
  "description": "根据当前用户有权访问的订单编号查询订单状态",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "订单编号，不是用户编号"
      }
    },
    "required": ["order_id"]
  }
}

这里的 parameters 是参数整体，type=object 表示参数是一个对象，properties 列出允许的字段，required 列出必须提供的字段。常见字段含义如下：

字段含义示例
name工具的唯一名称，应用据此找到真正的函数get_order
description说明工具用途和适用场景，帮助模型选择工具查询当前用户可访问的订单
parameters工具接收的参数整体定义一个 JSON 对象
type参数或字段的数据类型object、string、integer、boolean、array
properties对象中允许出现的字段列表order_id
required必须提供的字段列表order_id
字段内的 description解释参数应该传什么订单编号，不是用户编号

不同模型厂商或 SDK 可能把这段定义包装在 parameters、input_schema 或其他字段中，但核心含义相同：告诉模型输入对象有哪些字段以及每个字段的约束。接入时应以实际 API 文档为准。

除了基本字段，还可以增加范围、枚举和数组约束：

{
  "type": "object",
  "properties": {
    "page": { "type": "integer", "minimum": 1, "default": 1 },
    "status": {
      "type": "string",
      "enum": ["待支付", "已支付", "已取消"]
    },
    "include_items": { "type": "boolean", "default": false },
    "order_ids": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["page"]
}
  • minimum、maximum：限制数字范围；
  • minLength、maxLength：限制字符串长度；
  • enum：限制只能从给定选项中选择，适合状态和排序方式；
  • default：参数缺省时建议使用的默认值，最终是否补值由应用决定；
  • array 和 items：表示数组及其元素类型；
  • null：表示参数可以明确为空，不能把“缺失”和“空值”混为一谈。

参数描述应写清业务含义、单位、格式和边界。例如时间要说明使用 2026-10-09 还是时间戳，金额要说明单位是元还是分，订单编号要说明是否允许传多个编号。描述不清会让模型选错工具或生成错误参数。

参数校验的两层边界

参数校验至少分为两层：

校验层要检查什么失败示例
结构校验JSON 是否可解析、字段是否存在、类型、枚举和范围是否合法page 传成“第一页”
业务校验用户权限、资源归属、资源状态、幂等和操作风险用户查询了别人的订单

order_id 是字符串且格式正确，只能说明它“像一个订单编号”，不能说明订单真实存在，也不能说明当前用户有权查看。应用必须继续检查订单归属和访问权限。

建议的执行顺序是：

解析 JSON
  → Schema 类型和必填字段校验
  → 参数格式和范围校验
  → 用户、租户和资源权限校验
  → 幂等与风险检查
  → 执行真实工具

Schema 只约束输入形状，不能证明调用安全。工具执行前还应检查工具是否属于当前会话、资源是否属于当前用户、操作是否允许重复执行，以及是否需要人工确认。

校验失败时不要把异常堆栈直接返回给模型或用户，可以返回稳定的错误码和可操作的说明：

{
  "ok": false,
  "error_code": "ORDER_NOT_ACCESSIBLE",
  "message": "当前用户无权访问该订单",
  "retryable": false
}

retryable 可以帮助运行控制判断是否值得重试：参数错误和权限拒绝通常不可重试，网络超时或临时限流可能可以有限重试。错误结果应隐藏密钥、内部堆栈和超出用户权限的字段。

工具结果、重试与安全

工具结果也应使用稳定结构，而不是拼接一段难以解析的自然语言。成功和失败最好明确区分：

{
  "ok": true,
  "data": {
    "order_id": "A1001",
    "status": "已支付",
    "updated_at": "2026-10-09T10:30:00+08:00"
  },
  "source": "order-service"
}

模型可以根据 ok、data 和 error_code 决定回答用户、询问补充信息、改用其他工具还是停止任务。结果中应保留必要的来源和时间，便于模型解释结果和应用审计。

工具还要按风险分级：

类型例子默认策略
只读查询天气、搜索文档、读取订单可自动执行，但仍需权限和参数校验
可写创建草稿、修改个人设置校验幂等键，必要时提示用户
高风险付款、删除、发消息、发布内容必须人工确认，并记录审计日志

执行策略还应考虑超时、重试、限流、幂等和部分失败。对于付款、发货等不可重复动作，不能因为模型再次请求就直接重试，应使用业务幂等键查询上一次执行状态。工具失败后，应用应根据错误类型决定重试、切换工具、询问用户或结束任务，而不是让模型自行猜测结果。

工具定义、调用参数、校验结果、执行耗时、错误码、重试次数和最终停止原因都应纳入日志。日志需要脱敏，并能关联到本次 Agent 任务，方便定位是模型选错工具、参数错误、权限拒绝还是外部服务故障。

MCP：模型上下文协议

当一个 Agent 只需要查询订单时，应用可以直接注册 get_order 函数；但当多个应用都要连接文件、数据库、搜索和企业系统时，每个应用都单独编写适配代码，会造成重复开发和维护困难。MCP（Model Context Protocol，模型上下文协议）就是为了解决“外部能力如何被统一发现、描述、读取和调用”而设计的一套开放协议。

可以把 MCP 理解成模型应用与外部能力之间的连接约定：外部系统按照协议提供能力，支持 MCP 的应用按照协议发现和使用这些能力。MCP 是连接规范，不是 Agent、模型或某个具体工具；它也不会自动授予权限。

MCP 的角色和能力

MCP 通常包含三类角色：

角色负责什么例子
Host承载用户交互、模型和 Agent 运行循环的完整应用桌面助手、IDE、后端 Agent 服务
ClientHost 内维护 MCP 连接、发现能力并转发请求的组件MCP 客户端 SDK 或连接模块
Server对外提供工具、资源和提示模板的服务文件 Server、数据库 Server、企业 API Server

一个 Host 可以连接多个 Client，一个 Client 通常维护与一个 MCP Server 的连接。模型一般运行在 Host 中，Server 提供能力但不直接替模型决定下一步。

flowchart LR
    USER[用户] --> HOST[Host 应用]
    HOST --> MODEL[模型与 Agent Loop]
    HOST --> CLIENT1[MCP Client]
    HOST --> CLIENT2[MCP Client]
    CLIENT1 --> SERVER1[MCP Server A]
    CLIENT2 --> SERVER2[MCP Server B]
    SERVER1 --> DATA1[文件或数据库]
    SERVER2 --> DATA2[搜索或企业 API]

MCP Server 常见的三类能力如下：

能力解决的问题例子是否可能产生副作用
Tools要执行什么动作？查询订单、搜索代码、创建文件可能，写操作通常有副作用
Resources要读取哪份内容？文档、配置、文件、数据库记录通常不产生
Prompts用什么模板组织任务？分析错误日志、总结指定文档通常不直接产生

Tools 通常包含名称、用途说明和输入 Schema；Resources 通常通过 URI 或其他标识定位内容；Prompts 是可复用的提示模板。读取项目说明文档可以设计为 Resource，根据订单编号查询实时状态可以设计为 Tool，修改订单状态则是有副作用的 Tool。

Host 可以发现这些能力，但应先按当前用户、任务和安全策略筛选，再把允许使用的部分放入模型上下文。“Server 能提供”不等于“当前用户可以使用”。

MCP 的连接方式

传输层解决的是 Client 和 Server 如何交换协议消息；Tools、Resources、Prompts 解决的是交换什么能力。两者不要混为一谈。当前项目选型通常重点考虑 STDIO 和 Streamable HTTP，HTTP + SSE 主要用于兼容旧实现。具体 SDK 的版本和实现应以官方文档为准。MCP 传输规范

STDIO：本地进程通信

STDIO（Standard Input / Output，标准输入输出）通过操作系统的 stdin 和 stdout 传递消息。Client 启动 Server 子进程，写入请求并读取响应，双方通常在同一台机器上运行：

MCP Host
  └─ MCP Client ── stdin/stdout ── MCP Server 子进程
                                      └─ 文件、脚本或本地数据库

STDIO 适合 IDE、桌面应用、本地开发工具以及访问当前机器上的文件或代码仓库。Server 的协议消息必须写入 stdout，日志应写入 stderr，否则日志会混入协议数据导致解析失败。Client 还要处理子进程启动失败、退出码、超时和异常退出。STDIO 的进程权限通常等同于启动它的用户，不能因为“只在本机运行”就忽略文件系统和命令执行权限。

Streamable HTTP：远程或服务化部署

Streamable HTTP 使用 HTTP 连接 Client 和 Server，支持普通响应，也可以按需要返回流式消息，适合远程服务、容器部署和多个客户端共享：

MCP Host / Client
        │ HTTP 请求
        ▼
    网关、认证和限流层
        │
        ▼
MCP Server（数据库、搜索或企业 API）

远程部署需要配置认证、加密传输、超时、限流和网络访问控制。还要明确 Server 是否维护会话：有状态部署可能需要会话粘滞或共享会话存储；无状态部署更容易水平扩展，但每次请求都要携带完成处理所需的信息。是否支持独立的服务端推送、流式响应和会话恢复，要以具体 SDK 和规范版本为准。

HTTP + SSE：历史兼容方式

早期 MCP 实现常使用 HTTP + SSE（Server-Sent Events）：Client 通过 SSE 长连接接收 Server 消息，再通过 HTTP 请求发送调用。它可以支持服务端推送，但连接管理、反向代理和负载均衡更复杂。新项目应先确认 Client 和 Server 是否支持 Streamable HTTP；只有在兼容旧系统时才选择 HTTP + SSE。

对比项STDIOStreamable HTTPHTTP + SSE（兼容）
运行位置通常是本地子进程本地或远程服务通常是远程服务
通信方式stdin/stdout 双向通信HTTP 请求，可选流式响应SSE 接收 + HTTP 请求发送
典型场景IDE、本地文件、个人工具企业服务、容器、共享 Server旧客户端或历史部署
认证方式操作系统进程权限HTTP 认证、网关和证书HTTP 认证、网关和证书
扩展性受本机进程限制更适合服务化和水平扩展连接和会话管理更复杂
主要风险子进程权限过大、stdout 被污染网络暴露、会话和权限配置长连接、代理和断线处理

选择传输方式时，可以先回答三个问题：Server 是否必须访问本地资源？是否需要多个客户端远程共享？是否需要生产级认证、审计和扩展？本地单机工具通常从 STDIO 开始，远程共享服务通常选择 Streamable HTTP，旧系统才考虑兼容 HTTP + SSE。

一次 MCP 调用发生了什么

以“查询项目的构建失败记录”为例，完整流程通常是：

Host 创建或连接 Client
    → Client 与 Server 初始化并交换能力信息
    → Client 获取 Tools、Resources、Prompts 列表
    → Host 按权限筛选可用能力
    → 模型提出调用或读取意图
    → Client 请求 Server 执行或读取
    → Server 访问外部系统并返回结果
    → Host 写回模型上下文
    → 模型生成回答或继续任务

对应的时序如下：

sequenceDiagram
    participant H as Host
    participant C as Client
    participant S as Server
    participant D as 外部系统
    H->>C: 建立连接并初始化
    C->>S: 交换版本和能力
    C->>S: 获取工具和资源列表
    S-->>C: 返回能力描述和参数 Schema
    H->>C: 转发已校验的调用请求
    C->>S: 请求执行工具
    S->>D: 查询构建系统
    D-->>S: 返回结果
    S-->>C: 返回结构化结果或错误
    C-->>H: 写回模型上下文

这个流程中有两个容易混淆的地方：

  • 能力发现：Client 可以获取 Server 提供的列表，但 Host 仍要根据权限和当前任务筛选；
  • 真实执行：模型和 Host 决定是否调用，Server 负责执行自己的能力，外部系统返回的错误应转换成稳定错误信息。

MCP 与普通 Tool Calling 的区别

普通 Tool Calling 通常是某个应用直接注册函数并调用，主要解决“模型如何提出一次工具调用”。MCP 进一步规定了跨应用连接、能力发现、资源读取和提示模板复用，主要解决“外部能力如何被统一提供和复用”。

对比项普通 Tool CallingMCP
能力来源通常由当前应用本地注册可以来自独立的本地或远程 Server
能力发现应用代码提前写好Client 可以发现 Server 提供的能力
能力类型主要是函数调用Tools、Resources、Prompts
复用范围依赖具体应用适配多个支持 MCP 的 Host 可以复用
连接管理由应用自行实现由 MCP Client 和传输层约定
安全责任应用负责权限和执行Host 与 Server 共同负责权限和执行

MCP 不会自动把普通函数变成安全工具，也不会让模型绕过应用权限。它减少的是连接和适配的重复工作，身份认证、参数校验、资源权限、人工确认和审计仍需要由 Host、Server 及其业务系统完成。

部署选择与安全边界

MCP Server 可以作为本地进程运行，也可以作为远程服务运行：

  • 本地进程适合个人开发工具、IDE 插件和本机文件访问；
  • 远程服务适合团队共享的知识库、数据库和企业系统；
  • 远程连接必须配置认证、加密传输、访问控制、超时和限流；
  • Server 不应默认拥有整个文件系统或数据库的访问权限，应限制到必要目录、表和操作；
  • 对删除、付款、发送消息等高风险 Tool，应保留人工确认或审批；
  • 日志至少记录调用者、Host、Server、工具名、参数摘要、结果状态、耗时和停止原因；
  • 对连接断开、超时、重复调用和 Server 返回的未知状态制定恢复策略。

学习 MCP 时，应先掌握普通 Tool Calling、权限和错误处理，再学习协议连接和能力发现。这样才能理解 MCP 提供的是统一连接方式，而不是“连接成功后就自动安全”。

记忆

记忆不是“把所有历史对话永久塞进 Prompt”，而是根据任务需要保存、筛选、检索和删除信息。它至少包括当前任务状态、短期对话记忆、长期知识记忆和结构化实体记忆。

短期记忆

短期记忆保存当前会话中对后续回答仍有用的信息，本质上是对 LLM 上下文窗口（Context Window）的管理。除了历史消息，还应记录当前任务目标、已完成步骤、工具结果、错误和待办事项。

任务状态：正在生成月度报告
已完成：读取销售数据、计算增长率
待完成：生成图表、导出文件
用户约束：按人民币展示，保留两位小数

短期记忆的目标不是保存越多越好，而是在有限 Token 预算内保留会影响当前决策的信息。

实现方式：

  1. 全量消息缓冲（Conversation Buffer）：不做任何截断，把所有的聊天记录全量输入

  2. 滑动窗口缓冲（Sliding Window Buffer）：

  • 按“轮数”滑动：如果对话太长，丢弃旧的，把最近 N 轮的对话记录直接塞进 Prompt

  • 按“Token 数”滑动：动态计算 Token，只要总 Token 超过预设阈值，就把最老的一条消息踢出去

  1. 摘要记忆（ConversationSummaryMemory）：让 LLM 隔一段时间对之前的对话做一个“总结”
  • 设置一个触发器：比如对话达到 5 轮，或者总 Token 接近限制。
  • 触发时，单独发起一次大模型调用（后台静默进行）。【Prompt："这是之前的对话摘要：{旧摘要}。这是最近的新对话：{最近 5 轮}。请将新内容融入，生成一份更全面、简短的新摘要。"】
  • 拿到新摘要后，清空那 5 轮的原始聊天记录。
  1. 摘要 + 滑动窗口

维护两个存储区：一个存 Summary，一个存 Recent_Messages。当 Recent_Messages 长度超过 10 轮时：

  • 提取前 5 轮，扔给 LLM 去更新 Summary。
  • 将这前 5 轮从 Recent_Messages 中彻底删除。
  • 保留后 5 轮原封不动。

摘要需要保留时间、数值、用户约束、已确认结论和待办事项，并在更新后检查关键事实是否丢失。对话过长时可以优先删除寒暄和重复内容，但不能删除仍影响当前决策的约束。

长期记忆

长期记忆保存跨会话仍可能有用的信息，例如用户明确确认的偏好、已完成项目的结论或组织知识。本质是外部存储，但不等于向量数据库：结构化事实应使用关系型数据库或 JSON 按用户 ID 查询，适合语义匹配的历史经验才使用 Embedding + 向量检索。

写入长期记忆前，应判断信息是否稳定、是否得到用户确认、是否包含敏感数据，以及未来是否真的会被使用。临时任务状态、一次性的闲聊和未经确认的推测不应直接写入长期记忆。

实现方式（RAG 架构）：

  1. 存储阶段（Embedding & Storage）：

把用户的历史偏好、过去的复杂任务结果先通过 Embedding 模型（如 OpenAI 的 text-embedding-3-small）将文字转为向量（一串数字），再存入数据库（如 Pinecone, Milvus, Chroma）

  1. 检索阶段（Retrieval）：

当用户说“帮我像上次那样写个报告”时，程序将“上次写报告”这句话转为向量。在向量数据库中计算余弦相似度，找到最接近的历史记录。

  1. 注入阶段（Augmentation）：

把搜到的历史记录提取出来，作为“背景知识”塞进当前的 Prompt 中。Prompt 模板示例：“已知用户过去的偏好是：{检索到的历史记忆}。现在请回答：{用户当前问题}。”

实体记忆

对于用户的姓名、语言偏好、所属组织、不能吃的过敏原等实体信息，用向量检索很容易出错或找不全。更稳妥的方式是使用 JSON 文件或关系型数据库（MySQL/MongoDB）结构化存储：

{
  "user_id": 123,
  "language": "zh-CN",
  "dietary_restrictions": ["花生"],
  "updated_at": "2026-10-08"
}
  1. 基于 NER（实体提取）的被动写入

每次聊天结束后，用一个小模型（或在后台开一个低成本的独立线程）来处理对话。

  • Prompt 设定："阅读以下对话，提取用户的客观信息和偏好，并以 JSON 格式输出。如果没有新信息，输出空 JSON。"
  • 输出示例：
  • 更新数据库：存入数据库的用户画像表中。
  1. 处理记忆冲突

比如上个月画像里写了 {"job": "程序员"}，今天用户说“我辞职去送外卖了”。

  • 实现方式：不能直接覆盖，需要让大模型做“合并（Merge）”。
merge_prompt = f"""
已有用户画像：{old_profile_json}
最新对话内容：{new_chat}
请判断新对话是否与旧画像冲突，如果冲突，请以最新对话为准更新画像，如果新增，请补充。输出最终的 JSON。
"""

冲突处理不能只依赖模型自由发挥，还应结合更新时间、信息来源和用户确认状态，并保留变更记录。例如用户今天说“我已经不再对花生过敏”，系统应更新当前状态，同时保留旧值和更新时间，方便审计和恢复。

  1. 读取阶段

用户登录后可以根据 user_id 查询结构化画像，但不应把完整画像永远贴在 System Prompt 最开头。应根据当前任务选择必要字段，限制注入内容和 Token，并避免把敏感信息暴露给不需要它的工具。

记忆的生命周期与隐私

记忆系统应明确“写入、读取、更新、删除和过期”规则：

  • 用户可以查看、修改和删除自己的记忆；
  • 租户、用户和会话之间必须隔离；
  • 敏感字段应脱敏、加密或限制访问；
  • 长期未使用、过期或用户撤回的信息应清理；
  • 记忆来源和更新时间应可追踪，避免把模型推测当成事实。

RAG 检索

RAG（Retrieval-Augmented Generation，检索增强生成）是先从外部知识库检索相关资料，再把资料作为上下文交给模型生成答案。它适合处理模型训练数据中没有、变化快或需要引用来源的知识。

普通 LLM 可能不知道企业内部制度、最新产品文档或刚发生的业务数据。RAG 不直接修改模型参数，而是在请求时补充外部证据：

文档 → 清洗/分块 → Embedding → 向量库
用户问题 → 查询改写 → 召回 → 重排 → 上下文组装 → 模型回答

RAG 不能保证答案一定正确。错误分块、召回遗漏、权限过滤失效或文档本身过期，都会导致错误回答。因此必须保留来源，并允许在证据不足时拒答。

向量化处理流程

  1. 文档清洗：去除无效字符（如多余的换行符、HTML 标签、乱码等）。
  2. 文本拆分（Chunking）：按照特定策略将文档切分为 Text Chunks。
  3. 附加元数据（Metadata Enrichment）：为每个 Chunk 关联元数据（如：来源文件名、章节、页码、创建时间等）。这有助于后续的混合检索和过滤。
  4. 计算向量：调用 Embedding 模型，将 Chunk 转化为高维向量。
  5. 写入索引：将向量和原始文本、元数据关联存入向量数据库。

这条链路属于离线或准离线的知识库构建过程。在线回答时还需要另一条链路：用户问题先经过意图判断和查询改写，再进行权限过滤、召回、重排和上下文组装，最后才交给模型生成。

关键参数：

  • Chunk Size（分块大小）：通常以字符数或 Token 数衡量。常见大小为 250 - 1000 Token。
  • Overlap Size（重叠度）：相邻两个分块之间重叠的部分，通常设为 Chunk Size 的 10% - 20%，用于防止切片处的语义断裂。

文本拆分方案

分块没有固定的万能值，应根据文档类型和问题粒度调整。分块过小会丢失上下文，过大则降低召回精度并占用更多 Token。每个分块还应尽量保留标题、来源和更新时间，避免检索命中后无法判断它来自哪里。

常规文章 / 新闻 / 行业报告

无明显结构的长文本：这类文本通常由段落组成，语义相对连续。

  • 拆分方案：递归字符切分（Recursive Character Splitting）。
  • 实现逻辑：优先按段落（\n\n）切分，如果段落太大，再按句号（。）、逗号（，）或空格切分，直到满足目标 Block 大小。

技术文档 / API 手册 / Markdown

具有强结构性的文档：此类文档通常有明确的层级结构（如 H1, H2, H3 标题），直接按字数切片会破坏章节的完整性。

  • 拆分方案：基于结构的切分（Structure-Aware Splitting）。

  • 实现逻辑：利用 Markdown、HTML 或 PDF 的标题标签进行物理隔离。每个 Chunk 内部应保留其所属的各级标题作为上下文。

  • 示例：

    # 标题 1: 数据库连接
## 标题 2: 配置参数
这里是具体的配置参数介绍...

    切分时，应将“标题 1 -> 标题 2 -> 配置参数介绍”作为一个整体或将标题信息作为元数据附加到内容分块中。

FAQ / 常见问题集

问答对：FAQ 通常很短，且一个问答代表一个独立的知识点。

  • 拆分方案：不拆分（No Splitting / Single-Pair Chunking）。
  • 实现逻辑：不要将“问”和“答”拆开。每一个问答对直接作为一个独立的 Chunk 进行向量化。
  • 优化策略（Question-only Embedding）：通常用户的输入是问题，所以对 FAQ 进行检索时，仅对“问题（Q）”进行向量化并检索，召回后将对应的“回答（A）”提供给大模型。这种方式的检索准确率通常高于“对 QA 全文做向量化”。

源代码

代码具有极强的语法结构，按字符数硬切会导致语法报错或逻辑截断。

  • 拆分方案：语法树切分（Language-Specific AST Splitting）。
  • 实现逻辑：根据编程语言（如 Python, Java, JS）的语法，解析出类（Class）、函数（Function）或方法，并以此为边界进行切分。

结构化数据 / 表格

PDF 中的 Table、CSV：向量模型（Embedding）对表格等二维结构数据的语义理解能力相对偏弱。

  • 拆分方案：文本化转换 / 按行切分。
  • 实现逻辑：
    • 如果是小表格，可将其转换为 Markdown 表格格式 或 JSON 字符串，整体作为一个 Chunk。
    • 如果是大表格，可以按行拆分，并在每一行前附加上表头（Header）的字段名。例如：将一行数据转为“[表头 A]: [值A], [表头B]: [值B]”的文本格式再进行向量化。
  • 进阶方法：利用大模型对表格进行摘要（Summary），对摘要进行向量化检索，检索命中后返回原表格。

高级方案

父子分块

  • 痛点：为了高精度的检索，我们希望 Chunk 越小越好（语义更聚焦）；但为了大模型能生成合理的回答，我们又希望给大模型提供更大的上下文（Chunk 越大越好）。
  • 解决思路：
    1. 将文档切分为较大的父分块（Parent Chunks）（如 2000 字符）。
    2. 再将每个父分块切分为多个互相重叠的子分块（Child Chunks）（如 200 字符）。
    3. 只对子分块进行向量化并存入数据库，但向量数据库中需记录子分块与父分块的对应关系。
    4. 检索时：检索匹配子分块，但在喂给大模型时，自动替换为其对应的父分块。

假设性问题/文档生成

  • 痛点：用户的提问（Query）通常很短，而知识库中的文档（Document）通常很长，两者的向量空间分布可能不一致，导致检索效果不佳。
  • 解决思路：
    1. 用户输入问题。
    2. 利用 LLM 针对问题生成一个假设性的回答（Hypothetical Document）不需要保证其真实性，只要符合行业语言习惯。
    3. 进行向量化，并用这个向量去知识库中检索真实的文本块。
    4. 这种“文档检索文档”的方式，往往比“问题检索文档”具有更高的语义匹配度。

查询、召回与重排

用户问题往往口语化，检索前可以补全上下文、纠正错别字或拆分复杂问题，但不能改变实体、时间范围、权限和否定条件。原始问题和改写结果都应保留，便于审计和排查。

  • 关键词检索：适合产品名、错误码、合同编号等精确内容；
  • 向量检索：适合表达不同但含义相近的问题；
  • 元数据过滤：负责时间、租户、权限、文档类型和版本；
  • 混合检索：结合关键词和向量，减少单一方法的遗漏；
  • 重排：对候选文档按相关性、时效性、来源质量和去重结果重新排序。

召回阶段的目标是尽量不漏掉相关证据，重排阶段才重点提升前几条的准确性。重排后的结果还要去重、再次检查权限、处理冲突，并按 Token 预算组装上下文。不能把所有候选文档不加筛选地拼进 Prompt。

生成约束与引用

生成 Prompt 应明确要求模型只依据提供的资料回答，引用文件名、章节、页码或 URL；资料不足时说明“不确定”，不能用模型记忆补写。文档之间存在冲突时，应展示冲突来源并请求确认，而不是静默选择其中一份。

RAG 质量评估

评估需要拆成检索层和生成层：

  • 检索层：Recall@K、Precision@K、MRR、NDCG、权限过滤准确率；
  • 生成层：答案相关性、事实忠实度、引用正确率、拒答准确率和任务成功率。

应建立固定问题集和证据集，把召回遗漏、引用错误、越权和无答案误答等失败案例加入回归测试。只看最终回答是否“像是正确的”无法定位问题发生在分块、召回、重排还是生成阶段。

上下文工程

上下文工程（Context Engineering）关注的是“这一轮到底应该把哪些信息交给模型”。它比单独编写 Prompt 的范围更大，包含上下文的收集、筛选、排序、压缩、注入和清理。

一次请求的上下文可能来自：

系统规则
  + 用户当前输入
  + 最近对话和历史摘要
  + 当前任务状态
  + 相关长期记忆
  + 检索结果和引用信息
  + 可用工具定义
  + 用户权限和环境信息

上下文不是越多越好。无关内容会占用 Token、干扰模型判断，过长的工具说明还可能导致模型选择错误的工具。构建上下文时应遵循：

  • 先做权限过滤，再决定是否注入内容；
  • 优先放与当前目标直接相关、来源可靠且较新的信息；
  • 对历史对话做窗口截取或摘要，保留约束、结论和待办事项；
  • 为检索片段附带文件名、章节、页码和更新时间；
  • 将用户输入、外部文档和工具结果与系统规则分隔，降低注入风险；
  • 接近上下文窗口上限时，压缩或删去低价值内容，而不是盲目截断末尾。

因此，Prompt 更像“如何向模型提出任务”，上下文工程更像“为这次任务准备哪些材料”。

上下文的分层

为了避免不同信息互相污染，可以把上下文分成几层：

层次内容主要来源处理重点
规则层系统指令、权限和安全规则应用配置、用户身份优先级最高，不能被普通用户输入覆盖
任务层当前目标、计划、完成条件Agent 状态随任务推进更新
交互层当前问题、最近消息、摘要对话存储控制窗口和摘要质量
知识层RAG 片段、长期记忆、引用数据库、向量库过滤权限、时效和来源
能力层工具定义、参数 Schema、工具结果Tool/MCP只注入当前任务需要的能力

这几层不应简单地混成一段长文本。应用可以在内部分别维护它们，最后按稳定顺序组装成模型请求，并记录每部分的来源。

上下文构建流程

flowchart TD
    INPUT[用户输入] --> AUTH[身份与权限检查]
    AUTH --> STATE[读取任务状态]
    STATE --> MEMORY[筛选记忆]
    MEMORY --> RETRIEVAL[检索相关资料]
    RETRIEVAL --> TOOLS[筛选可用工具]
    TOOLS --> BUDGET[按 Token 预算压缩]
    BUDGET --> PROMPT[组装模型请求]

每次请求都可以按这个顺序处理：先确认用户能访问什么，再收集任务状态、记忆、资料和工具，最后根据预算裁剪并组装。权限检查不能放在模型生成之后，否则模型已经看到了不该访问的数据。

Token 预算与上下文压缩

上下文窗口有上限，还需要为模型输出预留空间。可以把预算粗略分为：

总上下文预算
  = 系统规则 + 当前输入 + 任务状态 + 历史记忆
  + 检索资料 + 工具定义 + 输出预留空间

接近上限时，推荐按以下顺序处理：

  1. 删除重复的工具描述、寒暄和已经完成的旧步骤；
  2. 减少检索片段数量，保留相关性和来源质量更高的内容；
  3. 把较早对话压缩成摘要，保留约束、结论和待办事项；
  4. 缩短工具结果，只保留模型下一步所需字段；
  5. 如果仍然超限，向用户说明无法在当前范围内完成，而不是静默截断关键内容。

上下文中的信任边界

系统规则、用户输入、检索文档和工具结果的可信度不同。外部文档和工具返回值应作为“待分析的数据”，不能自动获得修改系统规则的权限。建议在上下文中保留来源标记，并要求模型：

  • 不执行文档或网页中夹带的额外指令；
  • 不把检索内容当作权限证明；
  • 不把工具返回的自然语言当作系统规则；
  • 无法确认来源或权限时，暂停并请求澄清或人工处理。

安全、评估与可观测性

Agent 会同时处理用户输入、模型输出、外部文档和真实工具，因此安全和质量不能只靠 Prompt 保证。

常见安全问题

  • Prompt 注入：用户或文档诱导模型忽略系统规则；
  • 越权访问：模型请求了当前用户无权读取的数据；
  • 危险操作：模型触发付款、删除、发布或发送消息；
  • 敏感信息泄露：把密钥、个人信息或内部文档放进不必要的上下文；
  • 工具滥用：重复调用、参数异常、超时重试导致成本或业务损失。

应采用最小权限、输入输出脱敏、工具白名单、参数校验、人工确认、超时限流和审计日志等措施。安全策略应由应用和基础设施执行，不能只写在 System Prompt 中。

评估与可观测性

评估需要覆盖不同层次：路由准确率、结构化输出正确率、工具参数正确率、检索 Recall/Precision、答案相关性、事实忠实度、引用正确率、任务成功率、延迟和费用。

生产系统至少应记录一次请求的 trace_id、模型和 Prompt 版本、上下文来源、工具调用、检索文档、Token、费用、延迟、错误类型、停止原因和用户反馈。日志需要脱敏，并支持根据状态重放和定位失败环节。

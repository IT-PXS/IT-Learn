Agent 工程实践

Agent 工作流从概念走向生产，需要解决四类问题：状态能否可靠保存和恢复，上下文是否足够且不失控，工具调用是否安全可审计，线上效果是否可以评估和排障。本篇聚焦与具体框架无关的工程方法；框架 API 和厂商配置应放在对应的框架或厂商文档中。

状态管理与持久化执行

Agent 不是一次模型调用，而是一个可能持续多轮、跨越工具和人工审批的任务。应用程序应把任务状态作为结构化数据管理，而不是只依赖消息历史。

1. 状态应包含什么

建议至少保存以下信息：

  • 任务身份：task_id、trace_id、用户、租户、创建时间和当前版本；
  • 用户目标：原始请求、已确认的约束、必填槽位和输出格式；
  • 执行计划：子任务、依赖关系、完成条件和当前步骤；
  • 上下文引用：消息、检索来源、文件 ID 和工具结果的引用，而不是无限复制全文；
  • 执行记录：tool_call_id、参数摘要、结果状态、重试次数和外部请求 ID；
  • 控制信息：迭代次数、Token/费用预算、截止时间、取消标记和审批状态；
  • 交付结果：最终答案、引用、失败原因和用户反馈。

状态中的敏感字段应单独加密或存放在受控存储中。模型上下文只读取完成当前步骤所需的最小状态。

2. 用状态机约束任务生命周期

将任务状态定义为有限集合，避免通过一段自然语言猜测任务是否完成：

stateDiagram-v2
    [*] --> Created
    Created --> Running: 开始执行
    Running --> WaitingApproval: 需要人工确认
    WaitingApproval --> Running: 批准
    WaitingApproval --> Cancelled: 拒绝或取消
    Running --> WaitingTool: 等待异步工具
    WaitingTool --> Running: 工具完成
    Running --> Succeeded: 满足完成条件
    Running --> Failed: 不可恢复错误
    Running --> Cancelled: 用户取消
    Failed --> Running: 人工重试或恢复

每次状态转换应记录前一状态、后一状态、触发事件、操作者和时间。只有允许的转换才能执行；例如已经 Succeeded 的任务不能因为重复消息再次发起扣款。

3. 断点恢复与并发控制

长任务应采用持久化检查点：完成一个子任务后保存状态，再进入下一步。进程重启或网络断开时，从最近检查点恢复，不要让模型从头猜测已完成的动作。写入状态时使用版本号或乐观锁，防止多个 Worker 同时覆盖计划和工具结果。

暂停、取消和人工接管都应成为显式事件。取消后要阻止尚未开始的工具调用，并根据工具的可取消能力处理正在执行的任务；无法取消时至少记录状态，等待结果后执行补偿或人工核查。

上下文工程与记忆

上下文窗口是有限资源。把全部历史、检索文档和工具结果原样塞给模型，会增加费用和延迟，也会让旧信息干扰当前任务。

1. 分层管理上下文

可以将上下文分为四层：

层次内容管理方式
当前输入本轮用户请求和明确约束原样保留，作为最高优先级用户信息
任务状态目标、计划、槽位、已完成步骤结构化存储，按步骤更新
短期记忆最近消息、工具结果和中间结论按 Token 预算裁剪或摘要
长期记忆用户偏好、稳定事实和历史任务明确来源、时间和置信度，允许修正或删除

长期记忆不能把模型的猜测直接当成事实。写入前应确认来源、适用范围和用户授权；读取时按租户、用户和任务权限过滤。

2. 压缩、摘要和检索

接近上下文上限时，优先删除重复的工具原始响应和已经完成的中间推理，保留用户约束、关键结论、证据引用、未完成任务和失败状态。摘要应使用固定结构，并保留原始记录的 ID，必要时可以回查。

当前目标：分析 2023 年财务风险
已完成：收入、利润、现金流提取
关键证据：[doc-17, page-8]、[doc-21, page-12]
未完成：核对审计意见
约束：只使用 2023 年公开资料

上下文组装应设置硬上限：系统指令、用户约束和安全规则预留固定预算，检索内容按相关性和来源质量截取，工具结果按字段和长度过滤。没有证据时应让 Agent 继续检索或明确拒答，而不是用摘要填补空白。

失败恢复、降级与人工接管

Agent 的失败不只有“模型报错”。还包括工具超时、部分成功、数据冲突、预算耗尽、重复循环、权限拒绝和外部状态未知。每类失败都应有可预测的分支。

失败类型推荐处理
参数或 Schema 错误返回字段级错误，让模型修正一次，超过次数后转人工
瞬时网络错误只对幂等操作按退避策略重试
工具超时查询幂等键或异步任务状态，禁止直接重复写入
权限拒绝停止当前动作，说明缺少权限，不让模型绕过策略
检索为空或证据冲突改写查询、扩大允许范围或明确说明无法确认
重复调用或预算耗尽保存已有结果，停止循环并返回部分完成状态
状态未知暂停自动化，交由人工核查外部系统

降级策略应预先定义，例如从高能力模型切换到低成本模型、从实时工具切换到缓存数据、从自动执行切换到生成待审批草稿。降级不能放宽权限或跳过高风险确认。

工程实践：工具调用与安全边界

前文介绍了 Agent 如何选择工具和在循环中执行工具。本节进一步回答一个工程问题：模型提出的调用意图，怎样经过应用程序的约束后，才可以安全地变成真实动作？

明确职责边界

Tool Calling/Function Calling 只负责把模型的意图编码成结构化数据，模型本身不应拥有数据库连接、文件系统权限或网络凭据。真正的执行链路应由应用程序控制：

模型提出调用
  → 解析并校验 Schema
  → 校验用户身份、租户和权限
  → 检查业务规则和风险等级
  → （必要时）请求人工确认
  → 在受限运行环境中执行
  → 脱敏、截断并记录结果
  → 将工具消息写回 Agent 状态

应用程序是工具调用的信任边界。即使模型输出了合法 JSON，也不能跳过权限检查；即使用户本人有权限，也不能绕过金额、数据范围、审批状态和环境等业务约束。

工具契约：Schema、结果和错误

每个工具都应有稳定、最小化的契约，至少定义名称、用途、参数、返回值、错误类型、风险等级和幂等策略。参数使用枚举、长度、范围、格式和必填约束，避免让模型自由拼接 SQL、Shell 或 URL。

{
  "name": "refund_order",
  "description": "为已支付且符合规则的订单创建退款申请，不直接执行资金划拨",
  "risk_level": "high",
  "parameters": {
    "type": "object",
    "required": ["order_id", "amount", "idempotency_key"],
    "properties": {
      "order_id": {"type": "string", "pattern": "^ORD-[0-9]+$"},
      "amount": {"type": "number", "exclusiveMinimum": 0, "maximum": 100000},
      "idempotency_key": {"type": "string", "minLength": 16, "maxLength": 64}
    },
    "additionalProperties": false
  }
}

工具结果也要结构化，至少区分 success、retryable_error、permission_denied、validation_error、requires_approval 和 fatal_error。错误消息返回可供模型调整的信息，但不暴露堆栈、密钥、内部地址或其他租户数据。工具超时、部分成功和异步任务应返回明确的任务 ID 与当前状态，不能只返回“执行失败”。

按风险分级，而不是按工具名称分级

同一个工具在不同参数下可能有不同风险。建议把动作分为以下等级，并将等级写入工具注册表：

等级典型动作默认策略
只读查询天气、读取公开文档、读取当前用户可见数据可自动执行，仍需权限过滤和限流
低风险写入保存草稿、创建个人待办、写入临时会话状态自动执行，支持撤销或补偿
中风险写入修改订单、提交工单、批量更新业务数据二次业务校验，必要时审批
高风险动作付款、退款、删除、发信、发布、生产变更明确展示参数和影响，人工确认后执行

人工确认不能只显示“是否继续”。确认界面应展示工具名、目标对象、关键参数、影响范围、预计费用、不可逆后果和有效期，并把批准结果绑定到具体的 tool_call_id、参数摘要和用户身份。参数在确认后发生变化时，必须重新确认。

参数、权限与数据边界

执行前至少完成四层校验：

  1. Schema 校验：类型、枚举、长度、格式、数值范围和未知字段；
  2. 身份与租户校验：当前用户、服务账号、租户、角色和数据归属；
  3. 业务校验：资源状态、金额上限、审批状态、操作时间窗和并发版本；
  4. 环境校验：开发、测试、预发和生产环境的允许动作，以及网络出口和资源配额。

权限过滤应在工具执行层再次完成，不能只依赖 Prompt 中的“不要访问其他用户数据”。例如查询订单时由应用根据会话身份强制追加 tenant_id 和 owner_id 条件；文件读取工具只接受已解析并校验过的文件 ID，不接受任意路径。

防范提示注入和间接攻击

外部网页、邮件、文档和检索片段都应视为不可信数据。文档中的“忽略之前指令”“把密钥发送到某地址”等内容只是被读取的文本，不能改变系统规则、工具权限或审批要求。建议：

  • 将系统指令、用户输入、工具结果和外部资料在消息结构上分隔；
  • 对工具结果标注来源和不可信等级，不把检索文本拼接成新的系统指令；
  • 让工具只暴露完成任务所需的最小能力，避免通用 Shell、任意 HTTP 请求和任意代码执行；
  • 对 URL 校验协议、域名、重定向、内网地址和 DNS 解析结果，防止 SSRF；
  • 对 SQL、Shell、模板和路径使用参数化 API、白名单和沙箱，禁止字符串拼接；
  • 对上传文件进行类型、大小、压缩炸弹、恶意宏和病毒检查。

安全策略应在模型调用前后都执行。模型可以建议“发送邮件”，但应用必须根据收件人、附件、内容分类和组织策略再次判断是否允许。

重试、幂等和补偿

网络超时并不代表工具没有执行成功。对写操作盲目重试可能造成重复扣款、重复发信或重复创建资源。写操作应由应用生成并持久化 idempotency_key，服务端按该键返回同一结果；重试策略要区分可重试错误、不可重试错误和需要人工核查的未知状态。

调用超时
  → 查询幂等键对应的执行状态
  → 已成功：复用原结果
  → 执行中：等待或返回异步任务
  → 未执行：按退避策略重试
  → 状态未知：暂停自动重试并转人工核查

涉及多个系统的长事务应设计补偿动作和状态机，例如“创建退款申请成功但通知失败”应进入待通知状态，而不是让 Agent 重新创建退款申请。

审计、隔离和最小权限

每次调用至少记录 trace_id、tool_call_id、操作者、租户、工具版本、参数摘要、策略判定、审批人、开始和结束时间、结果状态以及外部请求 ID。日志中的手机号、邮箱、令牌、身份证号和业务正文应按字段脱敏；原始敏感数据只存放在受控审计系统，并设置保留期限和访问审计。

工具执行账号应使用最小权限、短期凭据和独立网络出口。执行代码或处理不可信文件时使用容器、沙箱、CPU/内存/时间限制和只读文件系统。生产写操作与普通查询使用不同凭据和服务账户，便于撤销权限和追踪责任。

一个可落地的工具执行检查表

上线前逐项确认：

  • 工具是否有清晰 Schema、版本和所有者；
  • 是否拒绝未知字段、越界数值、任意路径和任意 URL；
  • 是否在服务端重新检查身份、租户和业务权限；
  • 是否定义超时、限流、并发上限、重试和幂等键；
  • 高风险动作是否展示影响并绑定人工确认；
  • 失败、超时、部分成功和状态未知是否有明确分支；
  • 是否记录可审计但经过脱敏的调用链；
  • 是否有撤销、补偿或人工接管方案。

工程实践：生产评估与可观测性

离线评测回答“这个版本在固定问题上表现如何”，可观测性回答“线上某次请求发生了什么”。两者结合，才能定位问题来自路由、检索、工具、模型、数据还是用户目标变化。不要只用最终答案的主观好坏评价 Agent。

先定义任务成功标准

为每类任务定义可判定的输入、约束、期望输出和失败条件。以“查询订单并生成退款申请”为例，成功不只是回复一段文字，还包括：找到了当前用户有权访问的订单、金额计算正确、没有越权、在需要时完成审批、工具状态与最终回答一致。

建议把指标拆成四层：

层次评估问题示例指标
路由与规划是否选择了正确流程和子任务意图准确率、槽位完整率、计划完成率
工具与检索是否正确调用并获得足够证据工具选择准确率、参数准确率、Recall@K、Precision@K
回答质量是否基于证据完成用户目标相关性、事实忠实度、引用正确率、拒答准确率
业务结果是否安全、及时、可复现地完成任务任务成功率、人工接管率、重试率、SLO 达成率

安全违规、越权访问、错误写入和不应执行的工具调用应作为硬性失败，即使文本回答看起来流畅，也不能被平均分掩盖。

建立版本化评测集

评测集至少包含正常样例、边界条件、歧义表达、权限差异、提示注入、工具超时、空结果、冲突证据和高风险动作。每条样例保存输入上下文、用户权限、期望路由、允许工具、关键证据、结构化断言和评分标准。

将数据集、Prompt、模型、工具 Schema、检索索引和评分器都版本化。发布新版本前进行离线回归；线上发现 Badcase 后，保留脱敏输入、实际轨迹、失败原因和修复后的期望行为，加入回归集，避免同类问题反复出现。

自动评分与人工评分结合

能用确定性程序判断的内容优先程序评分：JSON Schema、工具参数、权限结果、数值计算、引用是否存在、订单状态和任务状态。开放式答案可以使用规则、参考答案、模型评审和人工抽样，但模型评审必须有明确评分标准、盲评和定期人工校准。

评分器本身也要评估：检查它是否偏好更长的答案、是否会被格式迷惑、是否能识别越权和无证据断言。对高风险任务保留人工复核，不能把单一 LLM 评分当作安全证明。

统一 Trace、Log 和 Metric

一次用户请求使用一个 trace_id，每次模型调用、检索、工具调用和人工审批建立子 Span。建议记录以下字段：

  • 请求：trace_id、会话和任务 ID、租户、入口、时间、脱敏后的输入摘要；
  • 模型：模型名、版本、Prompt/策略版本、采样参数、输入输出 Token；
  • Agent：当前状态、计划版本、迭代次数、停止原因和预算消耗；
  • 检索：查询、过滤条件摘要、索引版本、候选数、来源 ID、分数和去重结果；
  • 工具：工具版本、参数摘要、风险等级、权限判定、耗时、重试次数、结果状态；
  • 结果：引用、人工反馈、用户是否采纳、任务是否成功、错误类型。

指标应区分总量、成功和失败，并按模型、版本、租户、任务类型和工具维度切分。核心指标包括 P50/P95/P99 延迟、Token 和费用、工具错误率、超时率、循环终止率、人工接管率、引用覆盖率和任务成功率。高基数字段如完整用户输入不应直接作为指标标签，避免监控系统爆炸。

用状态和停止原因解释 Agent 行为

仅记录最终文本无法解释 Agent 为什么失败。每次循环应记录状态转移和停止原因，例如 completed、max_iterations、budget_exceeded、timeout、permission_denied、approval_rejected、repeated_tool_call 和 context_limit。生产日志保留足够的结构化摘要，使排查人员能重放流程，但不把内部思维链作为日志或评估依据。

flowchart LR
    A[请求] --> B[路由 Span]
    B --> C[模型 Span]
    C --> D{工具或检索?}
    D -->|检索| E[检索 Span]
    D -->|工具| F[权限与审批 Span]
    F --> G[执行 Span]
    E --> H[生成 Span]
    G --> H
    H --> I[结果与反馈]
    B -.-> J[指标与告警]
    E -.-> J
    G -.-> J
    H -.-> J

线上监控、告警和取样

告警应绑定用户影响和可执行动作，而不是只设置一个总错误率阈值。例如：P95 延迟持续超标时切换更快模型或缩小上下文；工具权限拒绝率突然上升时检查策略或租户配置；费用异常时降低预算并暂停高成本路由；引用覆盖率下降时回滚索引或重排版本。

对低风险请求可以按比例采样，对高风险调用、错误调用、人工拒绝和状态未知的写操作保留完整轨迹。采样规则要在日志中记录，避免只看到成功样本而误判系统质量。线上数据进入评测集前应脱敏、去重并经过访问控制。

发布、回滚与持续改进

模型、Prompt、工具 Schema、检索索引和策略都应有独立版本，并支持灰度、按租户放量和快速回滚。发布前比较关键指标与基线，发布后观察延迟、费用、失败类型、任务成功率和安全事件；发现硬性失败或明显回归时立即停止放量，而不是等待平均分恢复。

一个闭环可以写成：

离线评测 → 小流量灰度 → 线上 Trace/指标 → Badcase 聚类
    → 修复 Prompt/工具/检索/策略 → 回归评测 → 再次发布

最终报告应同时给出总体指标、关键分组、置信区间或样本量、已知失败案例和成本延迟取舍。只有当任务成功率、安全约束、延迟和费用都满足目标时，才能把一次评测结果视为可上线证据。

爱编程的小生2026/10/8大约 8 分钟

Ai Agent 文档完善主线（临时）

这是一份阶段性工作文档，用来承接当前对话中的整理结论。后续新会话应先阅读本文，再继续修改 Java/Ai/Ai Agent.md。文档完成后可删除或归档。

一、两份文档的边界

项目中有两份独立文档，不能混为一谈：

  • Java/Ai/Ai Agent.md
    • 面向初学者，解释 AI Agent 的完整知识体系；
    • 必须能够独立阅读，不能要求读者先读 Agent工作流.md；
    • 重点是概念、组件、运行机制和工程实践的完整理解。
  • Java/Ai/Agent工作流.md
    • 专门讲 Agent 工作流、检索链路、推理模式、工具治理和生产实践；
    • 可以作为更深入的专题文档，但不能被当作 Ai Agent.md 的隐含前置知识。

Ai Agent.md 中如果出现 Workflow、Agent Loop、RAG、MCP、Prompt 等术语，必须在本文件中先解释其含义、作用和边界。

二、写作目标

Ai Agent.md 的目标不是罗列术语，而是让读者循序渐进地回答这些问题：

  1. AI Agent 到底是什么？和普通 LLM 有什么区别？
  2. Workflow 是什么？为什么有些任务用 Workflow，有些任务需要 Agent？
  3. Agent 如何通过 Agent Loop 完成任务？
  4. Prompt、结构化输出、上下文、工具、MCP、记忆和 RAG 分别解决什么问题？
  5. 这些能力如何组合成一个可运行的 Agent？
  6. 如何处理权限、安全、失败、成本、评估和可观测性？

统一的讲解顺序应为：

概念定义
→ 与相邻概念区分
→ 简单例子
→ 执行流程
→ 组件和实现
→ 工程边界
→ 评估与治理

四、已经完成的整理

1. AI Agent 基础章节

已删除重复、粗糙的“关键能力、工作原理、技术实现”罗列，整理为：

  • Agent 基本定义；
  • Agent 与普通 LLM 的区别；
  • Workflow 的定义、例子、优点和局限；
  • Workflow 与 Agent 的对比；
  • Agent Loop 流程图、状态和停止条件；
  • Agent 核心组件：模型、状态/记忆、决策循环、工具、运行控制；
  • AIGC、Agent、AGI 的区别；
  • 什么时候适合使用 Agent，什么时候普通 LLM 或 Workflow 更合适。

原来引用本地图片的内容已移除，避免图片路径导致渲染错误。

2. Prompt 工程

已补充：

  • Prompt 的基本结构；
  • 角色、目标、背景、规则、工具、输出和失败条件；
  • 分隔符与提示词注入边界；
  • Zero-shot、Few-shot、结构化输出和分步任务说明；
  • 从“帮我查订单”逐步改写成可执行任务说明；
  • Few-shot 示例如何覆盖正常、缺失和混淆输入；
  • 模板变量、消息角色和规则冲突；
  • Prompt 缓存与响应缓存、长期记忆的区别；
  • 稳定前缀、动态内容、缓存命中率和 Token 复用率；
  • 缓存未命中排查、Token、延迟、费用和版本评估。

缓存相关内容需要区分通用原理与厂商实现。缓存命中率至少区分：

请求命中率 = 读取缓存的请求数 / 总请求数
Token 复用率 = 缓存读取 Token 总和 / 总输入 Token 总和

3. 结构化输出

已从 AI Agent 基础章节中拆出，成为独立二级章节，位置在 Prompt 工程之后、上下文工程之前。

4. 上下文工程

已作为独立二级章节，补充了：

  • 上下文来源和分层；
  • 权限过滤、任务状态、记忆、RAG、工具筛选；
  • Token 预算和上下文压缩；
  • 系统规则、用户输入、外部文档、工具结果的信任边界；
  • 上下文构建流程图。

5. Tool 工具调用

已详细补充：

  • 工具定义、模型意图和应用执行的边界；
  • name、description、parameters、type、properties、required；
  • enum、minimum、maximum、default、array、items、null；
  • Schema 结构校验与业务权限校验；
  • 错误码、retryable 和结构化工具结果；
  • 幂等、超时、重试、风险分级和人工确认。

6. MCP

已补充：

  • MCP 定义和作用；
  • Host、Client、Server；
  • Tools、Resources、Prompts；
  • STDIO、Streamable HTTP、HTTP + SSE；
  • 本地进程、远程服务和历史兼容方式的选型；
  • MCP 调用时序、普通 Tool Calling 对比和安全边界；
  • 多张 Mermaid 图：角色架构图、传输方式图、能力关系图、调用时序图。

传输方式的当前写法应保持谨慎：STDIO 适合本地进程，Streamable HTTP 适合远程服务，HTTP + SSE 主要作为历史兼容方式。具体 SDK 的版本和实现仍需以官方文档为准。

7. 记忆和 RAG

已补充基础内容：

  • 记忆：任务状态、短期记忆、长期记忆、实体记忆、冲突处理、生命周期和隐私；
  • RAG：知识库构建、清洗、分块、Embedding、召回、重排、上下文组装、引用、无答案策略和评估。

后续仍需继续检查它们是否与 Prompt、上下文和 Tool 章节重复，保持职责边界清楚。

五、后续完善重点

1. 继续打磨概念层

每个章节首次出现术语时都要说明：

  • 英文全称和中文含义；
  • 它解决什么问题；
  • 它不负责什么；
  • 一个简单的输入、过程和输出例子；
  • 与相邻概念的区别。

避免只写“可以提高效率”“实现智能化”等空泛表述。

2. 补充可执行示例

后续示例优先采用一个贯穿场景，例如“订单查询助手”或“企业知识库报告助手”，逐步展示：

用户输入
→ 意图和槽位
→ Prompt
→ 上下文组装
→ 工具调用
→ 记忆/RAG
→ 结构化结果
→ 验证与交付

每个示例都要说明正常路径、缺失参数、工具失败、权限拒绝和资料不足时怎么办。

3. 补充工程边界

每个能力都应回答：

  • 谁负责真正执行？
  • 谁负责权限校验？
  • 失败后是否可以重试？
  • 如何避免重复执行？
  • 如何停止和取消？
  • 如何记录来源、版本、成本和错误？

不要把 Prompt 描述当作权限控制，也不要把模型输出当作经过验证的业务事实。

4. 检查图文质量

图表应服务于理解目标：

  • 角色关系使用架构图；
  • 调用顺序使用时序图；
  • 步骤和分支使用流程图；
  • 方案比较使用表格；
  • 图前说明阅读目标，图后解释节点和边界。

Mermaid 图的节点文字保持简短，避免复杂标点导致渲染失败。不要使用不可移植的本地绝对图片路径。

5. 保持文档独立

修改 Ai Agent.md 时不能写“如 Agent工作流.md 所述”“见上一文”等隐含前置引用。必要的定义、流程和边界必须在本文件中重复说明。

六、后续编辑顺序

新会话建议按以下顺序继续，不要一次性重写整个文件：

  1. 检查 AI Agent 基础章节的定义、例子和 Agent Loop 是否连贯；
  2. 继续完善 Prompt 工程，补充模板设计、缓存、评估和失败案例；
  3. 完善结构化输出与结果验证；
  4. 完善上下文工程与 Token 预算；
  5. 检查 Tool、MCP、记忆、RAG 之间的边界和重复内容；
  6. 最后补安全、评估、可观测性、成本和部署；
  7. 每次只修改一个主题，检查标题层级、Mermaid、代码块和 diff。

七、编辑原则

  • 面向初学者，先解释再使用术语；
  • 先讲问题，再讲概念，再讲流程、例子和工程约束；
  • 章节独立，不能隐含依赖另一份文档；
  • 保留有助于理解的历史概念，但降低不必要的展开；
  • 不把模型能力、应用能力、工具能力和协议能力混为一谈；
  • 不用一个例子证明整体质量，加入边界和失败案例；
  • 不声称“完成”而不检查文档结构和格式。

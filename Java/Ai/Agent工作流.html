完整工作流

  1. 用户输入

用户发来文本、图片、文件、语音或操作请求。

  1. 上下文构建

整合当前输入、对话历史、长期记忆、系统规则、工具列表、用户环境、上传文件等。

  1. 意图识别与槽位填充

判断用户想做什么，并提取关键参数，例如时间、地点、预算、对象、格式等。

例如：老板这句话是想干嘛？是闲聊？是查资料？还是想订票？

  1. 路由与工具选择

判断是否直接回答，还是需要搜索、读文件、调用 API、执行代码、操作邮箱/日历等。

  1. 规划与任务拆解

对复杂任务制定计划，把大问题拆成多个子任务；简单任务可跳过复杂规划。

例如：这个问题太复杂了，我得拆成三步走。第一步查 A，第二步查 B，第三步对比。

注意：不是所有任务都需要复杂规划，简单问题可能直接回答，复杂任务才会拆解

  1. 执行循环

按计划反复执行：思考缺什么 → 调用工具/检索/计算 → 获得观察结果 → 判断是否继续。

  1. 检索增强流程

如果任务需要查资料，则进行：提 Q → 召回 → 重排 → 阅读 → 提取 → 整合。

  • 提 Q：把“我要那个谁的资料”翻译成 Search: 某某某 简历。
  • 召回：去数据库里捞出 20 篇相关文档。
  • 重排/阅读/提取：“这 20 篇文档里，第 3 篇和第 5 篇最有用，其他的扔掉。”
  1. 结果验证与约束检查

检查资料可靠性、时效性、冲突信息，并确认是否满足用户约束。

  1. 生成或行动

生成最终回答，或者执行真实操作，例如发邮件、创建日程、生成文件等。

  1. 反馈与迭代

根据用户反馈继续修改、补充、重新规划或执行下一轮任务。

工作流例子

你走进一家大公司（Agent）：

  1. 前台接待（意图识别）：
    • 你问：“洗手间在哪？” -> 接待员直接指路（闲聊/简单问答）。
    • 你问：“我想谈两个亿的生意。” -> 接待员把你带到会议室（进入复杂任务流程）。
  2. 项目经理（规划 & 提 Q）：
    • 你坐在会议室说：“我想了解你们公司去年的财务状况。”
    • 经理记下来，写在纸上：“去查 2023 年度财报、审计报告。”（这是提 Q）。
  3. 实习生（召回）：
    • 拿着纸条去档案室，抱回来一堆文件夹（这是召回）。
  4. 经理筛选（精排）：
    • 经理看了一眼，扔掉了一半不相关的，留下核心的三份文件。
  5. 最终汇报（生成）：
    • 经理根据这三份文件，口头向你汇报总结。

意图识别

意图识别（Intent Recognition）其实是 Agent 的交通指挥官（Router）。没有它，Agent 就是个无头苍蝇。

作用：

  1. 避免资源浪费（省钱、省时间）
  • 场景：用户说了一句：“你好呀！”
  • 没有意图识别：Agent 去把“你好呀”做提 Q，去数据库里疯狂召回几百条包含“你好”的文档，然后分析……最后回你一句“你好”。
  • 有意图识别：识别出意图是 Chit-chat（闲聊），不走搜索流程，直接调用大模型回复“你好！有什么我可以帮你的吗？”
  1. 精准调用工具（Tool Routing）

Agent 通常挂载了许多工具（搜索、天气查询、股票查询、绘图）。

  • 场景：用户说：“帮我画一只猫。”
  • 意图识别：识别出意图是 Text-to-Image（绘图）。此时 Agent 知道不要去知识库里搜索“猫的样子”，而是应该直接调用 DALL-E 或 Midjourney 接口；如果识别错意图（比如识别成搜索），它就会给你返回一堆猫的文字介绍，而不是一张图。
  1. 提取关键参数（槽位填充 Slot Filling）
  • 场景：用户说：“帮我订明天去上海的机票。”
  • 意图识别：Book_Flight`（订票）。
  • 槽位提取：
    • Time：明天
    • Destination：上海
    • Source：缺失，可能需要反问用户

提 Q

“提 Q”（Query Formulation / Refinement），全称通常理解为 “提取/提出 Query（查询词）”。

用户对他人的提问往往是口语化、模糊甚至缺失关键信息的。如果直接把用户的话拿去数据库搜索，效果通常很差。因此，Agent 需要对用户的原始问题进行改写、扩充或拆解，生成适合机器搜索的关键词或短句。

  1. 核心目的：把“人话”变成“机器搜索语言”。

  2. 作用：

  • 去噪与纠错：去掉“那个、哎呀、请问”等无意义词汇，纠正错别字。
  • 关键词提取：比如用户问“苹果最新的那个手机多少钱”，提 Q 可能会生成 iPhone 15 价格。
  • 意图改写：用户问“我电脑蓝屏了怎么办”，提 Q 可能会生成 Windows 蓝屏 解决方案、电脑死机 故障排除。
  • 问题拆解（Sub-queries）：针对复杂问题。比如用户问“对比一下特斯拉 Model 3 和小米 SU7 的续航”，提 Q 会拆解为两个查询：特斯拉 Model 3 续航里程 和 小米 SU7 续航数据。
  1. 总结：提 Q 就是让 AI 帮你想好“怎么在百度/谷歌/数据库里搜才能搜到答案”。

意图识别 与 提 Q 的区别

  1. 意图识别（Intent Recognition）：定方向。

决定是往东走（闲聊），往西走（搜索），还是往南走（画图），输出结果通常是一个标签（如：Search, Chat, Code, Plot）。

  1. 提 Q（Query Formulation）：做细活。

只有当方向确定为“搜索”后，才轮到提 Q 出场。它是把用户的话翻译成搜索引擎能懂的词，输出结果通常是搜索词（如：iPhone 15 pro max price）。

召回

“召回” （Recall）是信息检索（Search Engine）领域的经典术语。

在海量的数据库（比如企业文档、维基百科、互联网）中，有成千上万条数据。Agent 不可能把所有数据都塞给大模型去阅读（因为字数有限制且太贵）。召回就是从这片数据海洋中，快速筛选出几十条最相关的内容片段的过程。

  1. 核心目的：快速缩小范围，从“几亿条”筛选到“几十条”。

  2. 作用：

  • 关键词匹配（倒排索引/BM25）：就像查字典，文章里包含“iPhone”这个词，就被召回。
  • 向量检索（Vector Search）：这是 AI 时代的特色。它通过计算语义相似度来找资料。即使文章里没有“便宜”这个词，但有“性价比高”、“实惠”，向量检索也能通过语义理解把它召回。
  • 衡量标准：召回率（Recall Rate）。即“相关的文档你找回来了多少？”（宁可错杀一千，不可放过一个，通常召回阶段会稍微多拿一点数据，留给后面去精排）。
  1. 总结：召回就是在大海里撒网，把可能跟问题沾边的资料全部捞上来。

重排

在已经“召回”了一批候选资料之后，Agent 再对这些资料重新排序，挑出最相关、最可靠、最值得读的内容。

“召回”为了速度，用的是粗糙的算法（大海捞针，捞上来可能有沙子）。“重排”是用更精准（也更慢）的模型，把召回回来的 50 条内容，逐一打分，只留下分数最高的 TOP 3 给大模型

召回和重排的区别

步骤作用目标
召回 Recall从大量资料里捞出一批可能相关的内容宁可多捞，不要漏掉
重排 Rerank对召回结果重新排序、筛掉低质量内容宁可少而准，选最有用的

思维框架

COT

CoT （Chain-of-Thought）是处理所有需要推理的复杂任务时的核心技巧。

什么时候用 CoT？

  • 数学计算、逻辑推理、代码诊断
  • 多步骤分析、方案设计

Zero-shot CoT

请分析这道数学题。80 的 15% 是多少？
请一步步思考。

适用于数学计算、简单推理

引导式 CoT

在回答之前，先思考以下三个问题：
1. 这个问题涉及哪些关键变量？
2. 这些变量之间是什么关系？
3. 最终答案如何验证？

适用于多步骤分析、方案设计

结构化 CoT

在 <thinking> 标签中展示你的推理过程：
<thinking>
1. 首先，将 15% 转换为小数：15% = 0.15
2. 然后，计算 0.15 × 80 = 12
3. 最后，验证：12 / 80 = 0.15 ✓
</thinking>

在 <answer> 标签中给出最终答案：
<answer>12</answer>

适用于代码诊断、逻辑推理

ReAct

核心思想：思考 → 行动 → 观察 → 再思考 → 再行动 → 最终回答

即：Thought → Action → Observation → Thought → Action → Observation → Answer

用户：帮我查一下东京明天天气，适不适合跑步？

Thought：我需要知道东京明天的天气。
Action：调用天气工具。
Observation：明天东京 18-22℃，小雨。
Thought：需要判断是否适合跑步。
Answer：不太适合户外跑步，建议室内跑或等雨停。

适合场景：

  • 查资料；
  • 调用工具；
  • 多步任务；
  • 信息不完整的任务；
  • 需要边做边观察结果的任务。

实现方式

  1. ReAct Prompt 普通模板
你是一个可以使用工具解决问题的智能助手。

你需要根据用户问题，判断是否需要调用工具。
如果不需要工具，可以直接回答。
如果需要工具，请按照 Thought → Action → Observation 的循环解决问题。

你可以使用以下工具：

1. search
用途：查询最新或外部信息。
输入格式：
{"query": "搜索关键词"}

2. calculator
用途：进行数学计算。
输入格式：
{"expression": "数学表达式"}

工作流程：

Question: 用户问题
Thought: 分析当前需要什么信息
Action: 工具名称
Action Input: 工具输入
Observation: 工具返回结果
Thought: 根据观察结果继续判断
...
Final Answer: 最终回答

规则：
- 不要编造工具结果。
- 如果需要最新信息，必须调用 search。
- 如果涉及精确计算，必须调用 calculator。
- 如果工具返回信息不足，可以继续调用工具。
- 最多调用 5 次工具。
- 一旦信息足够，输出 Final Answer。

缺点：模型输出的内容是纯文本格式，不稳定，工程解析容易出错。

  1. ReAct Prompt JSON 格式模板
你是一个可靠的 AI Agent，负责帮助用户完成任务。

你的目标：
- 理解用户真实需求。
- 判断是否需要工具。
- 必要时调用工具获取信息或执行操作。
- 基于工具结果和上下文给出准确、简洁、可执行的回答。

工作原则：
1. 不要编造事实、数据、工具结果或操作结果。
2. 不需要工具时，直接回答。
3. 需要最新信息、外部事实、内部数据、文件内容或精确计算时，必须调用对应工具。
4. 每次只输出一个动作。
5. 每次工具调用后，根据 Observation 判断下一步。
6. 不要重复执行无意义的相同工具调用。
7. 信息不足时，可以继续调用工具；如果仍不足，要明确说明。
8. 达到最大工具调用次数后，基于已有信息给出最诚实的回答。
9. 不要向用户暴露内部推理过程。
10. 高风险操作必须先请求用户确认。

可用工具：

[search]
用途：查询互联网公开信息、最新信息、价格、政策、新闻、产品资料。
输入：
{
  "query": string
}

[calculator]
用途：进行精确数学计算。
输入：
{
  "expression": string
}

[knowledge_base_search]
用途：查询内部知识库、公司文档、项目资料。
输入：
{
  "query": string,
  "top_k": number
}

[read_file]
用途：读取用户上传文件内容。
输入：
{
  "file_id": string
}

工具选择规则：
- 最新信息、新闻、政策、价格、产品参数：使用 search。
- 公司内部资料、制度、项目文档：使用 knowledge_base_search。
- 用户上传文件：使用 read_file。
- 数学、金额、比例、统计计算：使用 calculator。
- 写作、翻译、润色、闲聊：通常不需要工具。
- 发送邮件、删除数据、付款、提交订单等高风险操作：先请求确认。

输出格式：
你每一轮只能输出以下两种 JSON 之一。

如果需要调用工具：
{
  "type": "tool_call",
  "tool": "工具名称",
  "input": {
    ...
  }
}

如果已经可以回答：
{
  "type": "final_answer",
  "answer": "最终回答"
}

停止条件：
- 已经获得足够信息。
- 工具连续失败或没有结果。
- 达到最大工具调用次数。
- 继续调用工具不会明显提升答案质量。

注意：
- 只能输出 JSON。
- 不要输出 Markdown。
- 不要输出 Thought。
- 不要编造 Observation。
- 不要调用不存在的工具。

模板改进调整

经典 ReAct

模型输出：

Thought: 我需要查询天气。
Action: search
Action Input: 东京明天天气

程序执行搜索，然后把结果拼回 prompt：

Observation: 东京明天 18-22℃，小雨。

模型继续输出：

Thought: 已经拿到天气，需要判断是否适合跑步。
Final Answer: 不太适合长距离户外跑步。

JSON ReAct

模型输出：

{
  "type": "tool_call",
  "tool": "search",
  "input": {
    "query": "东京明天天气"
  }
}

程序执行搜索，然后把结果作为消息追加：

{
  "role": "tool",
  "name": "search",
  "content": "东京明天 18-22℃，小雨。"
}

模型继续输出：

{
  "type": "final_answer",
  "answer": "东京明天 18-22℃，有小雨，不太适合长距离户外跑步。"
}

注意：JSON ReAct 提示词中没有像经典模板写工作流程，而隐藏在程序里，由外层程序循环来控制实现，在执行代码中必须设置 max_iterations（最大迭代步数）。达到步数后，强制退出并返回当前获取到的线索

用户输入
  ↓
LLM 输出 JSON 决策
  ↓
如果 type = tool_call
  ↓
程序调用工具
  ↓
程序把工具结果作为 Observation 放回上下文
  ↓
再次调用 LLM
  ↓
LLM 继续输出 tool_call 或 final_answer
  ↓
直到 final_answer

Plan-and-Execute

流程：制定计划 → 执行第 1 步 → 执行第 2 步 → 执行第 3 步 → 汇总结果

用户：帮我做一个日本 7 天自由行攻略。

Plan：
1. 确认城市路线
2. 查交通方式
3. 查景点开放时间
4. 安排每天行程
5. 估算预算
6. 输出表格

和 ReAct 的区别

框架特点
ReAct边想边做，动态调整
Plan-and-Execute先制定总计划，再逐步执行

适合场景：

  • 长任务；
  • 项目型任务；
  • 旅行规划；
  • 报告生成；
  • 竞品分析；
  • 多阶段执行。

Reflexion

核心思想：Agent 做完一次后，检查自己哪里做得不好，然后改进下一轮。

流程：执行任务 → 评估结果 → 反思错误 → 调整策略 → 再执行

用户：写一封销售邮件。

第一版写完后，Agent 自检：
- 开头太生硬
- 没有体现客户痛点
- CTA 不够明确

然后重写第二版。

适合场景：

  • 写作优化；
  • 代码调试；
  • 长任务迭代；
  • 多轮搜索；
  • 需要质量提升的任务。

MRKL

MRKL 可以理解为“专家系统 + 大模型路由”。

它把不同能力拆成模块：

数学问题 → 计算器
天气问题 → 天气 API
搜索问题 → 搜索引擎
数据库问题 → SQL 工具
普通聊天 → LLM
用户：帮我算一下 12.5% 年化收益，10 万本金 3 年后多少钱？

Agent 判断：
这是计算问题 → 调用计算器，而不是靠大模型心算。

适合场景：

  • 多工具系统；
  • 企业 Agent；
  • 客服 Agent；
  • 数据分析 Agent；
  • 工作流自动化。

AutoGPT

这类框架强调“目标驱动”。用户给一个目标，Agent 自己拆任务、执行、创建新任务、循环推进。

流程：目标 → 创建任务列表 → 执行任务 → 产生新任务 → 排序 → 继续执行

目标：帮我调研一个 AI 写作工具的创业机会。

Agent 自动生成任务：
1. 查市场规模
2. 查竞品
3. 查用户痛点
4. 查定价模式
5. 总结机会

适合场景：

  • 长周期研究；
  • 自动化任务；
  • 创业调研；
  • 市场分析；
  • 复杂项目拆解。

Critic / Reviewer

一个 Agent 负责生成，另一个 Agent 负责审查。

流程：Generator 生成答案 → Critic 挑错 → Generator 修改 → 最终输出

Debate / Multi-Agent Debate

多个 Agent 扮演不同角色，相互挑战观点。

Agent A：支持买特斯拉
Agent B：支持买比亚迪
Agent C：负责质疑两边
Agent D：最终裁判

适合场景：

  • 投资分析；
  • 策略决策；
  • 复杂方案评审；
  • 风险识别；
  • 论文/代码审查。

Human-in-the-Loop

关键节点让人确认，Agent 不完全自动执行。

Agent 草拟邮件 → 用户确认 → Agent 发送
Agent 推荐投资方案 → 用户确认 → 不自动下单
Agent 生成删除计划 → 用户确认 → 再删除文件

适合场景：

  • 发邮件；
  • 支付；
  • 删除数据；
  • 法律/医疗/金融；
  • 高风险操作。

关系

  1. CoT：负责想清楚
  2. ReAct：负责边想边做
  3. Plan-and-Execute：负责拆任务
  4. Reflexion：负责复盘改进
  5. MRKL：负责选工具
  6. Critic：负责挑错
  7. Multi-Agent：负责分工协作
  8. Human-in-the-Loop：负责安全控制

  ↓
RAG 查资料
  ↓

  ↓
ReAct 调工具执行
  ↓
Critic 检查结果
  ↓
Reflexion 优化
  ↓

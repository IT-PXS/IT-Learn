博客文章编写规范

本文适用于本项目 src 目录下的技术文章。目标是让文章能够被循序渐进地学习、被长期维护，并且在 VuePress 中稳定渲染。

一、写作前先确定文章定位

每篇文章先明确三个问题：这篇文章解决什么问题、读者需要哪些前置知识、读完后能完成什么操作。公共原理、框架 API、厂商配置和项目实战应分开组织，避免同一知识点在多篇文章中重复且互相矛盾。

推荐的学习顺序是：背景与问题 → 核心概念 → 工作流程 → 最小示例 → 常见变体 → 工程约束 → 实战练习 → 延伸阅读。后面的概念不得依赖读者提前知道尚未解释的术语；如果必须提前出现，应先给出一句定义并链接到详细章节。

二、Front Matter 规范

---
title: 文章标题
date: 2026-10-08 12:00:00
category: Java
tag:
  - Spring
  - Ai
description: 用一句话说明文章解决的问题和覆盖范围。
---
  • title 与正文主题一致，不在标题中堆砌关键词。
  • description 说明读者能学到什么，不写空泛宣传语。
  • category 使用项目已有分类；tag 使用稳定、可复用的主题词。
  • 涉及版本、模型、依赖或协议时，在正文开头明确版本和适用范围。
  • 文件名和标题保持一致，阶段性文章使用清晰的编号。

三、标题与章节结构

  • 一篇文章只使用一个一级标题；如果主题由 Front Matter 标题承担，正文可从 ## 开始，但项目内应保持一致。
  • 标题描述知识主题，不使用“补充”“其他”“杂项”等无法判断内容的名称。
  • 标题顺序应体现学习顺序。先定义，再解释流程，再写优化和工程实践。
  • 章节之间避免重复；需要回顾时使用链接或一句话总结。
  • 一个章节只解决一个主要问题，复杂主题拆为多个连续章节。

四、解释与示例规范

  • 先说明“为什么需要”，再说明“是什么”和“怎么做”。
  • 首次出现的英文术语给出中文、英文和简短定义。
  • 示例应从最小可运行版本开始，再逐步加入异常处理、权限、持久化和性能优化。
  • 示例中的类名、配置项、版本号和 API 必须与正文一致；不确定的内容注明“示意代码”。
  • 代码块标注语言；配置示例不要放真实密钥，使用环境变量或占位符。
  • 对比多个概念时优先使用表格；描述流程时使用编号或 Mermaid 图。
  • 不把模型内部思维链作为必须展示的学习内容，使用步骤摘要、工具调用记录和结果解释替代。

五、链接、图片与资源

  • 站内文章使用相对链接，文件改名或移动后同步检查所有引用。
  • 图片使用相对路径，例如 ![流程图](./文章目录/1.png)；禁止写本机绝对路径。
  • 图片应有有意义的替代文本；截图旁边说明读者需要观察的重点。
  • 外部资料给出文章标题和直接链接；涉及版本、规范和 API 时优先引用官方文档。
  • 不复制大段外部原文，使用自己的语言归纳并记录来源。

六、图文结合规范

图表的作用是降低理解成本、展示关系和帮助读者记忆；它不能替代必要的文字定义。每张图都应回答一个明确问题，并在图前说明“为什么需要看这张图”，在图后解释“读者应该从图中得到什么”。

1. 选择合适的图表类型

内容推荐形式适用问题
顺序和分支流程图事情先后如何发生，在哪些条件下分支
角色之间的交互时序图谁在什么时候调用谁，消息如何返回
模块和依赖架构图/关系图系统由什么组成，模块如何连接
多个方案比较表格方案在能力、成本、复杂度上有什么差异
配置和界面操作截图用户需要在哪个位置进行什么操作
数据变化和趋势图表数值如何变化，结论是否有数据支持
抽象概念类比图或分层图概念之间是什么关系，边界在哪里

不要用流程图表达静态结构，也不要用截图替代可以复制的代码和配置。一个简单事实、一段很短的步骤或只有一个对象的说明，通常不需要额外配图。

2. Mermaid 图的写法

项目中的流程、时序和结构关系优先使用 Mermaid，方便修改、适配主题和保持文本可维护。

流程图

flowchart TD
    A[用户输入] --> B[意图识别]
    B --> C{需要外部资料?}
    C -->|否| D[直接回答]
    C -->|是| E[查询改写]
    E --> F[召回与重排]
    F --> G[生成答案]

适合表达步骤、条件分支、循环和终点。节点文字尽量简短，详细解释放在图后；节点中避免使用可能被解析为语法的括号、引号、冒号和复杂箭头。

时序图

sequenceDiagram
    participant U as 用户
    participant A as 应用
    participant M as 模型
    participant T as 工具
    U->>A: 提交请求
    A->>M: 发送上下文和工具定义
    M->>A: 返回工具调用
    A->>T: 执行工具
    T-->>A: 返回结果
    A->>M: 写回工具结果
    M-->>A: 生成最终回答
    A-->>U: 返回结果

适合表达调用者、被调用者、请求、响应和循环。参与者名称统一，箭头方向必须与文字说明一致；如果存在异常、重试或人工确认，应在图中明确分支。

状态图

stateDiagram-v2
    [*] --> Running
    Running --> WaitingApproval: 高风险操作
    WaitingApproval --> Running: 用户批准
    WaitingApproval --> Cancelled: 用户拒绝
    Running --> Success: 满足完成条件
    Running --> Failed: 超时或连续失败

适合描述任务生命周期、审批状态和错误恢复。状态名称使用稳定的业务含义，不要直接使用无法解释的内部变量名。

3. 图文配套写法

推荐采用“三段式”：

  1. 图前：说明问题和阅读目标；
  2. 图中：只保留主流程、角色和关键分支；
  3. 图后：按图的顺序解释每个节点，并补充图中没有展示的异常、权限和边界条件。

4. 截图和静态图片

  • 截图只保留与当前步骤相关的区域，裁剪无关的浏览器标签、个人信息和密钥。
  • 图片文件名使用有顺序和含义的名称，例如 01-流程图.png、02-配置页面.png。
  • 图片旁边写明重点，不让读者自行猜测需要观察哪里。
  • 图片中的文字必须清晰可读；过小的截图应改为文字步骤或重新绘图。
  • 同一篇文章统一图片风格、字号、颜色和标注方式。
  • 图片内容发生变化时同步更新说明和引用，不保留与正文不一致的旧截图。

5. 表格和代码的配合

表格用于横向比较，代码用于展示可执行细节，文字用于解释原因和边界。不要把完整段落塞进表格，也不要把需要复制的配置只放在截图里。表格列数过多时拆成多个表格，移动端阅读优先保证关键信息完整。

七、准确性与可维护性

  • 区分事实、经验、推测和建议；不要把示例参数写成普遍规律。
  • 版本、价格、模型能力、依赖 API 和协议行为可能变化，写明核对日期或适用版本。
  • 发现旧内容不准确时，优先在原章节修正并保留必要的迁移说明，不要无提示地删除已有知识。
  • 重构文章前先保留原内容或通过版本控制确认差异；移动文件时先更新链接，再删除旧文件。
  • 每次修改后检查 Markdown 标题、代码围栏、表格、图片和站内链接。

八、把文章写好的完整流程

1. 先定义读者和学习结果

不要从“我知道哪些内容”开始写，而要从“读者需要解决什么问题”开始写。写作前先记录：

  • 目标读者是谁，是入门者、已有基础的开发者，还是需要查 API 的使用者；
  • 读者已经知道什么，哪些术语不能默认读者理解；
  • 文章要解决的一个核心问题是什么；
  • 读者读完后应该能解释什么、实现什么或做出什么选择。

一篇文章最好只有一个主要学习目标。一个主题包含多个层次时，拆成系列文章，并在开头说明阅读顺序。

2. 建立知识地图

写正文前先列出知识点之间的依赖关系，而不是直接按想到的顺序堆内容。可以使用下面的关系：

问题/背景 → 术语定义 → 核心组成 → 工作流程 → 最小示例
                                   ↓
                         边界、变体、取舍和工程实践

每个新概念都要回答“它解决什么问题、依赖什么、输出什么、下一步由谁使用”。如果一个章节出现了尚未解释的概念，应提前补一句定义或调整章节顺序。

3. 用一个主线案例串联知识

复杂主题应尽量使用同一个主线案例，而不是每一节换一个互不相关的例子。主线案例需要在开头说明背景、目标、输入和最终结果；之后每个章节都说明该知识点在案例中的作用。

类比必须完整，不能只留下“前台”“项目经理”之类的孤立词语。推荐统一使用下面的写法：

**类比**：在这个案例中，前台负责确认访客身份，对应系统的身份和权限检查；项目经理负责拆解任务，对应 Agent 的规划模块。

类比用于帮助理解，不能替代准确的技术定义；类比和真实实现不一致时，应明确指出差异。

4. 每个概念按固定问题展开

重要知识点至少交代以下内容：

  1. 它是什么；
  2. 为什么需要它；
  3. 它解决了什么问题；
  4. 它的基本工作流程是什么；
  5. 最小示例如何实现；
  6. 常见变体和适用场景是什么；
  7. 有什么限制、风险和失败情况；
  8. 如何验证实现是正确的。

不要只介绍“怎么调用 API”，还要说明调用前提、输入输出、异常情况和适用边界。

5. 采用渐进式示例

代码和配置建议分四层展开：

  1. 最小示例：只展示核心概念，确保读者能看懂主流程；
  2. 可运行示例：补充依赖、配置、入口和必要的数据；
  3. 异常示例：展示参数错误、超时、空结果、权限失败和外部服务失败；
  4. 工程示例：加入日志、重试、限流、持久化、安全和测试。

每次只引入一个新变量。不要在第一个示例中同时加入数据库、缓存、消息队列、权限和监控，否则读者无法判断每部分的作用。

6. 解释选择和取舍

技术文章不仅要写“能怎么做”，还要写“什么时候这样做”。涉及方案对比时，至少说明：复杂度、性能、成本、可靠性、可维护性和适用场景。

例如介绍 Workflow 和 Agent 时，应说明流程确定性、灵活性、调试难度和 Token 成本，而不是简单宣布某一种方案更好。结论要绑定前提，避免把个人偏好写成普遍规律。

7. 用证据支撑结论

  • API、配置项、协议行为和版本兼容性优先查官方文档；
  • 性能、成本和效果结论注明测试条件，不能只写“更快”“更省”；
  • 来自实践的经验标记为“实践建议”或“经验总结”；
  • 引用第三方文章时用自己的语言归纳，并链接到原文；
  • 对可能变化的内容写明版本和核对日期。

8. 编辑文章，而不是只追加内容

初稿完成后至少进行三轮检查：

  1. 结构检查：删除重复内容，调整依赖倒置的章节，确保每节都服务于主线目标；
  2. 表达检查：拆分过长句子，统一术语，删除口语化但没有信息量的句子；
  3. 验证检查：运行示例，核对版本、链接、图片、代码围栏和最终结论。

补充新知识时，优先放入它所属的章节；只有无法归入现有结构时才新增章节。修改旧文章时保留原有有效内容，使用增补、改写和迁移说明，避免无理由大段删除。

九、文章质量标准

一篇合格的文章应该同时满足：

  • 可理解：初次阅读者知道文章在解决什么问题；
  • 可跟随：章节顺序和示例步骤没有跳跃；
  • 可验证：读者可以运行示例或依据明确标准检查结果；
  • 可迁移：读者理解原理后，能把方法应用到相近问题；
  • 可维护：版本、来源、链接和已知限制记录清楚；
  • 有边界：明确什么时候不适用、可能失败以及如何处理。

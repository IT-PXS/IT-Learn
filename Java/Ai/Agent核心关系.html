Prompt：先让模型理解要做什么

最初使用大模型时，人与模型之间只有一次输入和一次输出。用户把问题写进去，模型根据这段文字生成回答。模型并不知道用户真正想达到什么结果，也不知道哪些内容必须遵守，输入说得越含糊，输出就越容易偏离目标。

例如，用户说：“帮我写一份客户流失分析。”模型可以立即写出一篇结构完整的分析报告，但它不知道分析哪段时间、使用哪些数据、客户流失的统计口径是什么，也不知道报告是给管理层阅读，还是给运营人员制定挽回方案。文字看起来专业，并不代表任务已经被正确理解。

Prompt 解决什么问题

Prompt 是应用交给模型的任务说明。它把自然语言需求补充成模型可以执行的目标、约束和交付要求，例如：

任务：分析 2026 年第三季度客户流失率上升的原因。
范围：只分析国内直营渠道，排除主动注销的测试账号。
口径：流失率 = 本季度流失客户数 / 季初活跃客户数。
要求：区分数据已经证明的原因和仍需验证的假设，不补造数据。
交付：给出变化幅度、主要客户群、证据来源和后续核查建议。

这段 Prompt 让模型知道四件事：任务要达成什么目标，数据范围如何限定，哪些判断不能越过证据，最终结果应该怎样交付。角色、示例、输出格式和错误处理规则，也都属于任务说明的一部分。

Prompt 工程的重点不是寻找一句神奇的咒语，而是消除歧义、补足约束、定义完成标准，并用实际案例验证模型是否在缺少信息、遇到冲突或无法确认时做出正确反应。

Prompt 的能力边界

Prompt 可以告诉模型“应该查询客户数据后再分析”，却不能让模型凭空获得客户数据；可以写“只能访问当前用户有权限的数据”，却不能替代数据库的权限判断；可以要求“不要发送未经确认的邮件”，却不能阻止程序直接调用邮件接口。

因此，Prompt 适合解决“模型应该怎样理解和回答”，不负责提供外部事实，也不负责真正执行外部动作。对于只需改写文字、总结用户已经提供的材料等任务，一份清楚的 Prompt 通常已经足够。

但“分析第三季度客户流失率”需要真实的订单、客户和客服记录。模型即使知道应该怎样分析，也仍然缺少分析依据。要解决这个问题，需要把任务相关的信息提供给模型，这就进入了 Context。

Context：再让模型看到当前需要的信息

Prompt 解决了任务说明，却没有解决事实来源。假设模型只收到“分析第三季度客户流失率”，它只能列举价格、产品质量、服务体验等常见原因，无法判断本公司的客户究竟因为什么离开。

应用可以把客户表、订单表、客服投诉和产品变更记录放入模型输入。模型获得资料后，才有可能比较不同客户群的变化，寻找投诉和流失之间的关系，并引用具体记录。

Context 不只是更长的输入

Context（上下文）是某一轮模型调用实际能够看到的全部材料。它通常包括：

  • 当前用户请求和任务规则；
  • 已确认的任务状态和前面步骤的结果；
  • 对话中的必要内容和经过授权的长期记忆；
  • 从知识库检索出的资料；
  • 工具定义、工具返回值和外部环境信息；
  • 用户身份、权限和当前运行限制。

最简单的做法是把所有文件一次性塞给模型，但这很快会产生新的问题：无关资料占用上下文空间，旧版本制度和新版本制度互相冲突，重复记录掩盖关键证据，模型也可能无法判断某个数字的来源和适用范围。

所以 Context 工程关注的不是“能放多少文字”，而是这一轮任务需要哪些信息、哪些信息更可信、它们应按什么结构出现。例如定位异常客户群时，可以提供聚合统计和客户分群结果；核查流失原因时，再提供相关投诉和服务记录；生成最终报告时，只保留已验证结论、代表性证据和可回查的来源。

Context 的作用

应用通常通过几种方式准备上下文：

读取任务状态
  → 根据当前步骤选择所需资料
  → 检索相关文档或调用业务工具
  → 进行权限、版本和时间范围过滤
  → 压缩、去重并标记来源
  → 按 Token 预算组装本轮输入

如果要回答“第三季度流失率为什么上升”，上下文至少应让模型知道统计口径、比较基准、变化幅度、异常客户群以及与这些客户相关的业务证据。资料不足时，系统应该让模型说明缺口或继续检索，而不是让模型用常识填补空白。

Context 的能力边界

上下文中的资料不一定真实。检索可能漏掉关键文档，工具可能返回错误时间范围，摘要可能丢掉否定条件，外部文档还可能包含试图改变模型行为的提示词。把内容放进 Context，只代表模型可以看到它，不代表应用已经证明它正确。

同时，Context 仍然只是输入材料。模型可以根据材料提出“查询投诉记录”“生成图表”等行动，但应用还需要有一套机制来执行、验证和控制这些行动。于是问题从“模型看到了什么”进一步变成了“模型提出的行动如何被可靠地执行”，这就是 Harness 要解决的问题。

Harness：给模型接上受控的执行环境

当任务只要求生成文字时，应用在模型返回结果后就可以结束。现在把任务改成：“查询客户数据，生成流失分析报告，发送前让我确认。”系统就必须连接数据库、统计服务、图表生成器、文件存储和邮件服务。

模型可以提出一个结构化的工具调用：

{
  "tool": "query_churn_stats",
  "arguments": {
    "period": "2026-Q3",
    "channel": "domestic_direct"
  }
}

这段 JSON 只是模型的行动意图，并没有真的查询数据库。应用必须判断工具是否存在、参数是否合法、用户是否有权访问这些数据，再执行查询并处理返回结果。

Harness 解决什么问题

Harness 可以理解为包围模型的运行时支架。它把模型与上下文、工具、任务状态、权限、审批、预算和观测系统连接起来，负责把模型提出的行动转化为受控的程序执行。

一次工具调用至少要经过：

模型提出行动
  → 解析结构化输出
  → 校验工具和参数
  → 取得真实用户身份并检查权限
  → 执行工具
  → 校验返回数据的范围、格式和完整性
  → 写回任务状态和运行轨迹

Harness 还要处理工具超时、部分成功、重复调用、进程重启和高风险操作。例如，查询超时后可以查询异步任务状态，但不能盲目重复执行可能产生扣款的写操作；生成报告后可以先保存草稿，发送邮件前暂停并等待用户确认。

Harness 为什么不只是 Tool 集合

Tool 只描述“能够做什么”，Harness 还要规定“什么时候可以做、做完后如何确认、失败后怎样恢复”：

运行问题需要的 Harness 机制
查询完成前能否生成报告？保存步骤状态并检查前置条件
查询结果是否真的属于第三季度？校验时间范围、统计口径和数据完整性
邮件发送前是否需要确认？设置审批节点并暂停任务
工具超时能否重试？按错误类型和幂等性决定重试策略
应用重启后如何继续？持久化检查点和任务状态
为什么这次报告发错了？保存 Prompt、Context、工具调用和结果

Harness 解决了执行和控制问题，但任务仍然可能需要多次行动。第一次查询后，模型可能发现数据缺失；核查投诉后，可能需要改查某个批次；证据充分后，才应该生成报告。让这些观察结果影响下一步，就需要 Loop。

Loop：根据反馈持续推进任务

如果应用把“查询、统计、生成报告、发送邮件”写成固定步骤，遇到查询结果为空或证据互相矛盾时，流程只能执行预先写好的分支。开放式任务的下一步往往取决于当前结果，不能在运行前全部确定。

Loop（循环）就是让 Agent 反复经历“读取当前状态、提出下一步、执行行动、观察结果、判断是否继续”的机制。

一次 Loop 如何运行

以客户流失分析为例：

第一轮：比较第二季度和第三季度 → 发现流失率集中在客户群 A
第二轮：查询客户群 A 的流失原因 → 发现“交付延迟”占比上升
第三轮：核对物流记录和客服投诉 → 判断证据是否相互支持
第四轮：整理已确认结论和待验证假设 → 生成报告草稿
第五轮：用户确认报告 → 发送报告或根据反馈修改

每一轮通常包含四个动作：

  1. 读取目标、约束、已完成步骤、最新观察结果和剩余预算；
  2. 根据这些信息决定询问用户、检索资料、调用工具、修改结果还是结束；
  3. 由 Harness 校验并执行行动；
  4. 把结果写回状态，检查完成条件、风险和运行上限。

Loop 的关键在于反馈会改变下一轮的输入。第一次查询发现某个客户群异常，下一轮就不应继续重复整体统计，而应该围绕异常寻找证据。

Loop 不是无限自动运行

“继续循环”不等于“永远让模型自己决定”。如果没有停止条件，模型可能重复查询、反复修改已经合格的报告，或者为了优化某个指标不断扩大行动范围。

因此，Loop 必须设置：

  • 任务完成条件，例如关键结论已有来源、报告通过校验；
  • 最大迭代次数、总耗时、Token 和费用预算；
  • 重复行动检测和连续失败上限；
  • 用户取消、人工确认和暂停恢复机制；
  • 完成、暂停、取消、失败等明确状态。

Loop 中的反馈也不等于模型自动学习。当前任务中的反馈只会改变当前状态；如果要长期改进 Prompt、Skill、Workflow 或工具校验，应把失败案例加入评测集，修改后重新验证。

防止错误和目标漂移

假设查询工具错误地返回了全年数据，模型却把它当成第三季度数据继续生成图表。后续步骤越多，错误传播得越远，这就是级联错误。Harness 应在每个关键步骤设置验证点，Loop 在验证失败时回到修正或补查分支。

目标漂移则发生在系统逐步偏离原始要求时。例如用户要求“降低流失率，但不能通过拒绝高风险客户来实现”，系统如果只追踪流失率这个数字，可能把高风险客户排除在统计之外。任务状态中应分别保存目标、禁止事项和停止条件，每一轮继续执行前都重新检查。

四者之间的工程关系

Prompt、Context、Harness 和 Loop 不是四个互相替代的产品，而是一次 Agent 运行中的不同层次：

层次主要问题具体职责
Prompt模型应该怎样理解任务？定义目标、规则、边界和交付要求
Context模型当前需要看到什么？组织状态、记忆、检索资料、工具结果和环境信息
Harness模型提出的行动怎样安全执行？管理工具、权限、状态、审批、预算、恢复和观测
Loop根据行动结果怎样继续推进？读取反馈、选择下一步、修正任务并判断停止

四者在运行时连接成一条链路：

用户提出目标
  → Harness 读取任务状态
  → Context 工程组装本轮输入，其中包含 Prompt
  → 模型提出回答或行动
  → Harness 校验并执行行动
  → 工具结果写回状态
  → Loop 判断继续、询问、交付或停止
  → 继续时重新组装下一轮 Context

因此可以按这样的顺序学习：先用 Prompt 把任务说清楚，再用 Context 提供完成任务的材料；当模型需要访问外部系统时，用 Harness 约束并执行行动；当下一步依赖中间结果时，再用 Loop 驱动多轮推进。

实际系统不一定要一次实现四层。固定路径可以继续使用 Workflow；只有确实需要根据观察结果动态选择下一步时，才引入 Agent Loop。Prompt、Context、Harness 和 Loop 的增加，应当对应具体问题，而不是为了让系统看起来更复杂。

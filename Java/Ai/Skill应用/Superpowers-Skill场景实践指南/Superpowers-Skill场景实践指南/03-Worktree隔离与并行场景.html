Worktree 隔离与多 Agent 并行开发

本章解决一个常见问题：功能 A 还没做完，又想开始功能 B，但不希望两者的代码、提交和运行环境互相影响。主要对应 using-git-worktrees，结合 dispatching-parallel-agents 展示隔离与并行的配合。

本文依据本机安装的 using-git-worktrees 与 dispatching-parallel-agents 技能说明整理。示例中的路径、分支和功能名称需要替换；这份文档没有实际创建 worktree、启动 agent 或修改业务项目。

先理解：隔离与并行是两件事

能力解决的问题不自动解决的问题
Git 分支分别记录不同功能的提交历史同一目录中的未提交修改不会因新建分支自动隔离
Git worktree同一仓库拥有多个独立工作目录，可同时检出不同分支数据库、端口、Docker 等外部资源不自动隔离
using-git-worktrees检查已有隔离环境，安排工作目录、分支及基线验证不会自动判断所有功能依赖和业务验收标准
dispatching-parallel-agents把独立问题交给多个 agent 同时处理，汇总并验证结果不保证自动创建 worktree，也不保证任务之间没有依赖

worktree 共享仓库的对象和分支引用，但各自拥有工作文件、暂存区和检出的 HEAD。同一普通分支通常不能同时检出到两个 worktree，所以每项并行开发应使用各自分支。

多个 agent 也可能共享同一个目录。分配任务前必须明确它们使用哪个绝对路径、哪个分支、可以修改哪些文件；不能只说“开两个 agent”就认为已经隔离。

示意布局如下，路径仅作示例：

D:/item/example-app                  → feature/A，保留正在开发的功能 A
D:/item/example-app-worktrees/B      → feature/B，开发功能 B
D:/item/example-app-worktrees/C      → feature/C，开发功能 C

原目录可以继续有未提交修改。只要新 worktree 从明确的提交创建，原目录的未提交修改就不会自动带过去。忽略文件和未跟踪文件，例如 .env.local，也不能假定已被复制。

场景一：A 没做完，先独立开发 B

适合：两个功能可以独立交付，你希望保留 A 的开发现场。这是最值得先尝试的场景，不需要同时使用多个 agent。

复制发送：

项目：<项目绝对路径>
当前正在开发功能 A，现在要独立开发功能 B：<目标与验收条件>。

使用 using-git-worktrees skill 为 B 安排独立工作目录。
先检查仓库根目录、当前分支、已有 worktree 和未提交修改。
保留 A 的目录、分支及所有已有修改，不切换原目录的分支。

B 的基线：<明确的分支或提交，例如 origin/main>。
B 的新分支：<例如 feature/B>。
如果使用远程跟踪分支，先检查是否需要 fetch，记录实际基线提交。
不要把 A 的未提交修改复制过去。

先检查平台是否已有适用的隔离工作区能力；已处于适合本任务的
独立 worktree 时复用。需要创建时采用适用的平台能力或 Git worktree。
如隔离创建失败，报告具体原因，不退回 A 的目录修改代码。

在 B 的目录中准备依赖和必要配置，运行适合项目的基线检查，
再完成 B。按锁文件和项目约定选择包管理器。
不得自动连接共享生产数据库或启动可能影响 A 的服务。

完成后报告 B 的绝对路径、分支、基线提交、修改文件和验证结果。
本次不提交、不推送、不合并，也不清理 worktree。

预期结果

你能明确找到两个目录：原目录继续做 A，新目录只做 B。B 的构建、测试和后续编辑都在 B 的绝对路径下执行。

如果基线检查已经失败，应记录失败原因与影响，再决定能否继续验证新改动；不能将原有失败算作 B 引入，也不能省略不通过的检查。

模板中“不提交”等要求是你对本次执行的明确约定，会覆盖技能中的默认提交步骤。创建本地分支与创建代码提交是不同操作。

场景二：B 需要 A 的代码，基线怎么选

创建 worktree 时，选错基线会导致新功能缺少依赖，或者意外包含尚未准备交付的代码。

B 与 A 的关系建议基线需要考虑的后续工作
完全独立已确认的主分支提交分别审查、合并
B 必须调用 A 的新接口A 中已提交、可用的明确提交通常先集成 A，再处理 B 的审查基线
两者都需要同一套公共接口改造先完成公共接口任务，再从其明确提交开始约定接口后再分工，避免双方分别修改公共实现
A 只有未提交代码，B 又依赖它先整理出可共享的提交，或暂缓依赖部分新建 worktree 不会自动继承这些未提交代码

不要为了让 B 编译通过，把 A 整个目录直接复制过去。这样会把依赖、临时文件和未完成修改混入 B，难以审查。

复制发送：

功能 B 依赖功能 A 的 <具体接口或模块>。
先检查 A 的相关代码是否已提交，列出可选基线及影响。
给出推荐的基线提交、合并顺序和 B 的审查范围。
这一步只分析，不修改或提交 A 的现有代码。
如必须先提取公共改动，列出需要提取的文件及理由。

从 A 的提交创建 B 后，A 的后续提交不会自动出现在 B。需要有计划地同步依赖，并重新验证。若 A 最终以 squash 等方式合并，还需重新检查 B 的差异范围，避免在审查中重复展示 A 的改动。

场景三：两个独立功能交给两个 Agent 同时开发

适合：需求已明确，两个功能没有实现顺序依赖，修改范围可以划分。若目标不清楚，先参考 01 需求澄清与设计。

先填写一张分工表：

项目功能 B功能 C
目标<功能与验收条件><功能与验收条件>
工作目录<独立绝对路径 B><独立绝对路径 C>
分支feature/Bfeature/C
基线<提交编号><提交编号>
修改范围<目录或模块><目录或模块>
验证方式<测试、构建、交互检查><测试、构建、交互检查>
运行资源<端口与测试数据资源><另一组端口与测试数据资源>

复制发送：

项目：<项目绝对路径>。
请结合 using-git-worktrees 与 dispatching-parallel-agents，
安排两个子 agent 并行完成下面两个独立任务：

B：<目标、范围、验收条件>。
C：<目标、范围、验收条件>。

先核实依赖关系和公共文件修改风险。
如果任务互相依赖，先完成公共前置工作，再并行其余部分。
分别准备独立 worktree 和分支，并记录实际基线提交。
每个 agent 必须在指定的绝对路径执行命令和编辑文件。

向每个 agent 提供完整但精简的任务说明：
目标、目录、分支、允许修改范围、禁止修改范围、接口约定、
验收方式，以及需要返回的证据。
共同入口、依赖清单、锁文件和数据库迁移由一个负责人协调。
遇到跨任务需求时先交给协调者判断，不自行扩大修改范围。

各 agent 返回修改文件、验证命令与结果、未解决问题。
协调者审查两个结果并说明集成顺序及风险。
本次不提交、不推送、不合并，保留两个 worktree 供审查。
若工具不能保证指定目录下的独立写入，改为顺序实施；
不得让两个 agent 在同一目录无约束地同时修改。

预期结果

两个任务可以同时推进，但不是两份“已完成”消息就代表验收通过。你应收到各自的路径、差异范围、验证结果，以及组合后需要检查的行为。

在当前任务里调用子 agent 与创建两个新的用户任务不同。前者由当前协调者汇总结果；如果希望在侧边栏分别长期跟进，可以明确要求创建两个独立任务，并为每个任务指定隔离工作区。

场景四：功能 A 开发中，临时修一个 Bug

适合：当前功能还没完成，但需要修复已经上线或主分支中的问题。

复制发送：

保留当前功能 A 的目录、分支和未提交修改。
从 <需要修复的版本对应分支或提交> 创建独立 worktree，
新分支为 <例如 fix/export-error>。

使用 systematic-debugging 排查 <复现步骤和实际现象>。
先验证根因，再进行最小修复和相关回归检查。
仅处理这个问题，不带入 A 的未完成代码。
完成后报告修复差异与验证证据，先不要提交、推送或合并。

修复应从受影响版本的合适基线开始，不一定是当前最新主分支。修复集成后，A 是否需要同步它，应根据实际依赖判断。

同时运行时，还要隔离哪些东西

代码目录分开后，下面这些资源仍可能相互影响：

资源可能出现的问题处理方式
服务端口第二个服务启动失败，或浏览器访问到错误服务为各任务指定不同端口，记录实际访问地址
数据库一边执行迁移或清理数据，另一边测试异常使用独立测试数据库或 schema，检查真实连接配置
Rediskey 覆盖、缓存清理互相影响按应用能力使用独立实例、逻辑库或 key 前缀
Docker Compose项目名、固定容器名或端口发生冲突核对项目名、端口和卷；仅改项目名未必足够
环境变量文件新目录缺配置，或仍指向共享环境单独准备必要配置，不在报告中输出密钥
依赖与构建产物新目录缺依赖，或绝对路径输出覆盖别处按项目约定安装依赖，核对输出和缓存路径
后台任务与测试数据同时消费队列、发送通知或重置数据采用独立测试资源，按需关闭不相关的后台任务

如果本次只运行静态检查，不需要为了“隔离完整”额外启动整套服务。隔离程度应匹配实际要执行的操作。

开发完成后，怎样把结果放回主分支

各分支单独通过，不代表合并后的组合也通过。两个功能即便修改不同文件，也可能在路由、接口约定或业务行为上冲突。

建议按以下顺序收尾：

  1. 分别审查 B、C 的需求符合度和代码差异。
  2. 按明确授权分别提交，避免把无关修改混入提交。
  3. 确定集成目标和顺序，在合适的集成工作区组合修改。
  4. 解决文本冲突，检查接口和业务行为冲突。
  5. 在组合后的代码上重新运行适合的测试、构建和关键交互验证。
  6. 确认结果已保存、分支去向明确后，再清理不需要的 worktree。

复制发送，先做只读审查：

请审查 <B 的 worktree 路径> 和 <C 的 worktree 路径>。
分别依据各自记录的基线，检查本次提交及暂存、未暂存、未跟踪的新文件。
报告各功能的需求符合度、修改范围、验证结果和集成风险。
建议合并顺序，以及组合后必须验证的行为。
本次只审查，不提交、不合并、不删除目录或分支。

之后若要实际集成，再明确要求提交与集成到哪个分支。未提交改动不会因为合并分支自动进入目标分支。

清理前检查未提交和未跟踪文件、仅保存在本地的配置、尚未保存的工作成果。手动管理的 worktree 使用 Git 的移除方式；平台管理的工作区优先使用对应平台流程。不要把强制删除目录当作常规收尾步骤。

可选：理解手动 Git 命令

下面是 PowerShell 示例，假设路径、main 分支均真实存在，目标目录和新分支尚未创建。仅供理解和手动操作，不代表本次已经执行。平台有合适的工作区管理能力时，优先采用平台流程。

# 查看原目录的当前状态和已有 worktree
git -C 'D:/item/example-app' status --short --branch
git -C 'D:/item/example-app' worktree list

# 从本地 main 的当前提交创建 B；本地 main 不保证与远程同步
git -C 'D:/item/example-app' worktree add -b feature/B 'D:/item/example-app-worktrees/B' main

# 确认 B 的分支和基线
git -C 'D:/item/example-app-worktrees/B' status --short --branch
git -C 'D:/item/example-app-worktrees/B' rev-parse HEAD

后续安装依赖、构建和测试也必须在 B 的目录里执行。如果希望使用更新后的 origin/main，先获取远程更新并核对提交，再将创建命令的基线改为该引用。

示例选择仓库外的兄弟目录。如果使用仓库内的 .worktrees/，需先确认该目录被 Git 忽略，防止把整个工作目录纳入提交。

常见卡点

问题原因与处理
已经建了两个分支，为什么修改还是混在一起？分支不等于工作目录；在同一目录切换分支可能保留兼容的未提交改动。使用独立 worktree 才能同时保留不同开发现场
B 看不到 A 刚写的代码从主分支创建 B 不包含 A；即便从 A 创建，也只包含指定基线中的已提交代码
两个 agent 各用一个终端，是否就隔离了？终端不是隔离边界，检查它们实际的工作路径和分支
worktree 报分支已经被使用先查看 worktree 列表，使用现有正确目录或为新任务创建不同分支，不强行绕过检查
新目录启动失败先检查依赖、环境配置、端口和外部服务，不直接判定为新功能缺陷
两边都通过，合并后失败可能存在业务或接口冲突，需要组合后的回归验证
多开 agent 反而更慢拆分过细、任务强依赖或共享文件过多，会增加沟通、上下文与集成成本；改为顺序实施

当前 using-git-worktrees 技能含有隔离创建失败后退回原目录的默认指引。为了满足本章“保护 A 的开发现场”的目标，上面的模板明确覆盖该行为：隔离失败时不进入 A 修改。它还包含提交忽略规则等默认步骤；本次若不允许提交，应在任务中明确写出。

第一次实践的验收清单

  • 能说清楚 A 和 B 各自的绝对路径、分支及 B 的基线提交。
  • A 原有的修改保持原样，B 的开发只发生在 B 的目录中。
  • B 的依赖和必要配置已准备，检查命令在正确目录执行。
  • 实际同时启动服务时，端口与可写测试资源已检查。
  • 输出包含真实验证结果和未验证事项，而非仅有“开发完成”。
  • 提交、推送、集成和清理均符合本次明确约定。

先用“保留 A，在独立 worktree 完成一个小功能 B”熟悉目录与分支关系，再增加第二个 agent。需要进一步安排实施和审查时，可参考 04 计划执行与 Agent 分工 与 07 代码审查与反馈处理。

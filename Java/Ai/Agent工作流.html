Agent 与 Workflow

  1. Workflow 的执行路径主要由代码预先定义
  2. Agent 则由模型根据当前状态和工具结果动态决定下一步

实际项目常采用混合架构：主流程由 Workflow 控制，在路径不确定的节点嵌入 Agent Loop。能提前写清步骤且可靠性要求高的任务优先使用 Workflow；开放式研究、故障排查等难以预先写死路径的任务再使用 Agent。

完整工作流与例子

下面用同一个例子贯穿完整流程：用户走进一家大公司，对 Agent 说：“帮我了解这家公司 2023 年的财务状况，列出主要风险，并整理成一份报告。”在这个类比中，用户是提出任务的访客，Agent 是负责接待、调研和汇报的项目经理，搜索、档案库和计算器是项目经理可以安排使用的工具。

  1. 用户输入

用户发来文本、图片、文件、语音或操作请求。

类比：访客来到公司前台，明确告诉接待人员：“我想了解这家公司 2023 年的财务状况，并请你整理一份报告。”这是整个任务的原始需求。

  1. 上下文构建

系统整合当前输入、对话历史、长期记忆、系统规则、工具列表、用户环境和上传文件，并先检查用户是否有权访问相关资料，再依据 Token 预算筛选真正相关的上下文。

类比：前台接待先确认访客身份和权限，查看是否有预约，再把访客的来访目的、公司已有资料和可联系的部门交给项目经理。前台不会把所有档案都搬到会议室，只准备与本次来访有关的材料。

  1. 意图识别与槽位填充

系统判断用户想做什么，并提取完成任务所需的参数。这个例子中：

  • 意图：“公司财务研究与报告生成”；
  • 槽位：包括公司名称、年份 2023、关注指标“财务状况和主要风险”、输出格式“报告”；
  • 如果缺少公司名称或年份等必填槽位，应先向用户追问，而不是直接进入检索。

类比：前台先判断访客是问路、投诉、求职还是商务洽谈，这一步是意图识别；如果判断为商务洽谈，再记录“合作金额、合作对象、会议时间”等具体信息，这些具体字段就是槽位。把访客转交给项目经理属于下一步的路由，不属于槽位填充。

  1. 路由与工具选择

系统根据意图和槽位决定走哪条处理路径：直接回答、搜索公开资料、读取内部文件、查询数据库、调用计算器，或在涉及敏感操作时请求人工确认。路由只决定能力入口，工具真正执行前还必须校验权限和参数。

类比：前台判断该访客需要进入财务研究流程，于是把他交给财务项目经理；项目经理再决定联系档案室、财务部门还是审计部门，而不是让前台自己阅读所有文件。

  1. 规划与任务拆解

对复杂任务制定计划，例如：查找 2023 年度财报 → 查找审计报告 → 提取收入、利润和现金流 → 对比风险提示 → 整理引用。简单任务可以跳过复杂规划；如果外部事实变化或工具失败，计划应在检查点重新规划。

类比：项目经理把访客的目标写成任务清单，安排实习生先找年度财报，再找审计报告，之后提取关键数字，最后整理成报告。任务清单是计划，不是已经得到的结论。

  1. 执行循环

Agent Loop 按“读取状态 → 模型决策 → 调用工具/检索/计算 → 获得观察结果 → 写回状态 → 判断是否继续”反复执行。建议记录当前计划、工具调用、观察结果、迭代次数、Token/费用预算和任务状态。

执行循环中的停止条件：

  • 模型给出满足 Schema 的最终结果；
  • 已获得足够证据，继续检索不会明显提升质量；
  • 达到最大迭代次数、Token/费用预算或总超时；
  • 工具连续失败、重复调用或触发权限/安全策略；
  • 用户取消任务或要求人工接管。

类比：实习生每次从档案室拿回一批文件，项目经理先查看结果，再决定继续查找、改查其他资料，还是已经足够可以写报告。若档案室连续找不到资料，项目经理会停止继续派单并向访客说明情况。

  1. 检索增强流程

如果任务需要查资料，则按“提 Q → 召回 → 重排 → 阅读 → 提取 → 整合”执行：

  • 提 Q：把“我想了解这家公司去年的财务状况”改写成 公司名 2023 年度财报、公司名 2023 审计报告 风险 等查询。保留实体、时间范围、权限和否定条件；复杂问题可拆成多个子查询。
  • 召回：使用关键词检索、向量检索或混合检索，从数据库中取回候选文档。关键词适合公司名、编号和精确术语，向量检索适合语义相近表达，元数据过滤负责年份、租户和权限。
  • 重排：对候选文档按相关性、时效性、来源质量和权限重新排序，保留最值得阅读的内容。
  • 阅读与提取：从高分文档中提取收入、利润、现金流和风险因素，并保留文件名、章节、页码或链接。
  • 整合：去重、处理冲突、控制上下文 Token，要求最终结论能够追溯到来源。

类比：项目经理先把访客的问题写成“查 2023 年财报和审计风险”的检索单；实习生从档案室抱回 20 份可能相关的文件，这是召回；项目经理按相关性和可信度筛出 3 份核心文件，这是重排；随后阅读并摘录关键数字，最后整理成带出处的汇报材料。

  1. 结果验证与约束检查

检查资料可靠性、时效性、权限、冲突信息和用户约束。没有足够证据时应明确说明未知，不应依靠模型记忆补写。对数字、日期、计算结果和工具返回值优先使用程序校验。

类比：项目经理把报告中的数字与原始财报逐项核对，发现两份报告数据不一致时标注差异并继续确认，而不是选择一个数字悄悄填进去。

  1. 生成或行动

生成最终回答，或者执行真实操作，例如发邮件、创建日程、生成文件。发送消息、付款、删除、发布和修改生产数据等高风险动作需要人工确认；Function Calling 只表达调用意图，应用程序负责真正执行。

类比：项目经理根据已核对的资料向访客汇报，并生成报告文件。如果访客要求把报告发送给公司高管，项目经理需要确认收件人和发送权限，不能仅凭模型的一句话直接发出。

  1. 反馈与迭代

根据用户反馈继续修改、补充、重新规划或执行下一轮任务。生产系统应支持暂停、取消、人工接管、部分结果交付和失败恢复，并记录 trace、模型版本、Prompt 版本、Token、费用、延迟、工具调用和检索来源。

类比：访客指出报告缺少现金流分析，项目经理根据反馈新增任务，重新查找相关资料并更新报告；如果访客取消调研，项目经理应停止后续任务并保存当前进度。

意图识别

意图识别（Intent Recognition）是 Agent 对用户目标进行分类的过程，回答“用户想完成什么任务”。它决定后续应该直接回答、进入检索、调用工具、执行工作流，还是请求人工处理。

意图识别解决什么问题

没有意图识别，所有输入都可能被错误地送入搜索、RAG 或工具调用流程，既浪费时间和 Token，也会得到不符合用户目标的结果。

  • 用户说“你好呀”，应识别为 Chit-chat，直接回复，不必检索知识库。
  • 用户说“帮我画一只猫”，应识别为 Text-to-Image，路由到图像生成工具，而不是搜索猫的资料。
  • 用户说“帮我订明天去上海的机票”，应识别为 Book_Flight，进入订票流程，而不是直接给出旅游建议。

意图、槽位与路由的区别

这三个概念经常被混在一起：

概念要回答的问题示例
意图识别用户想做什么？Book_Flight（订机票）
槽位填充完成这个任务需要哪些参数？出发地、目的地、日期
路由接下来交给哪条流程或哪个工具？订票工作流、天气工具、人工客服

例如“帮我订明天去上海的机票”：意图是订票；槽位是出发地、目的地和日期，其中出发地缺失；把请求交给订票工作流是路由。缺少必填槽位时，应先向用户追问，不能让工具猜测。

意图识别的输出

建议输出稳定、可校验的结构化结果，而不是一段自由文本：

{
  "intent": "Book_Flight",
  "confidence": 0.96,
  "slots": {
    "source": null,
    "destination": "上海",
    "date": "明天"
  },
  "missing_slots": ["source"],
  "next_action": "ask_clarification"
}

confidence 不能替代业务校验。低置信度、多个意图冲突、缺少关键槽位或用户表达含糊时，应澄清问题或转人工。涉及付款、删除、发送等高风险操作时，即使意图识别置信度很高，也必须经过权限检查和确认。

实现方式

  1. 规则/关键词：速度快、可解释，适合意图数量少且边界明确的场景。
  2. 分类模型：适合意图集合稳定、拥有标注数据的场景。
  3. LLM 结构化分类：适合表达灵活、意图变化快的场景，但必须配合枚举、Schema、置信度和兜底策略。
  4. 混合路由：先用规则处理高确定性请求，再让模型处理复杂或未知请求。

类比：前台先判断访客是问路、投诉、求职还是商务洽谈，这一步是意图识别；如果判断为商务洽谈，再记录合作金额、合作对象和会议时间，这些具体字段就是槽位；把访客交给项目经理属于路由，不属于槽位填充。

提 Q（查询改写）

“提 Q”更准确的名称是查询改写（Query Formulation / Query Reformulation）。它发生在意图识别确认需要搜索或知识库检索之后，回答“应该用什么问题去检索”。

为什么需要查询改写

用户问题往往口语化、模糊、带有省略或错别字，直接检索会造成召回不足或召回偏差。查询改写把用户语言转换为更适合搜索引擎、数据库或向量库的查询表达。

例如：

  • “苹果最新的那个手机多少钱” → iPhone 最新型号 价格；
  • “我电脑蓝屏了怎么办” → Windows 蓝屏 故障排查；
  • “对比特斯拉 Model 3 和小米 SU7 的续航” → 特斯拉 Model 3 续航、小米 SU7 续航。

常见改写方式

  1. 去噪与纠错：删除“那个、哎呀、请问”等无检索价值的表达，修正错别字。
  2. 关键词提取：保留实体、属性、时间和动作，例如产品名、价格、版本。
  3. 上下文补全：结合历史对话补足省略的主语、时间范围和限定条件。
  4. 问题重写：把口语问题改成完整、明确的检索问题。
  5. 问题拆解：将比较、统计或多目标任务拆成多个子查询。
  6. 多查询扩展：生成不同表达方式，合并召回结果，降低单一措辞造成的漏召回。

查询改写的边界

查询改写不能改变用户原意，也不能擅自添加未经确认的事实。必须保留实体、时间范围、权限范围、否定条件和数据范围。租户、用户权限和数据类型应作为结构化过滤条件传递，而不能只写在自然语言 Query 中。原始问题和改写结果都应保留，便于审计和排查。

意图识别与查询改写的区别：意图识别决定“走搜索、闲聊、绘图还是订票”；查询改写只在确定要搜索后，把用户问题翻译成搜索系统更容易理解的表达。

类比：项目经理先确认访客确实要查财务资料（意图识别），再把“帮我看看这家公司去年的情况”写成“公司名 2023 年度财报、审计报告和风险提示”（查询改写）。前者决定是否进入档案室，后者决定交给档案管理员什么检索单。

召回

召回（Recall）是从大量候选数据中找出一批“可能相关”的文档或记录，回答“哪些内容值得进入下一轮筛选”。它的首要目标是覆盖相关信息，而不是一次就选出最终答案。

常见召回方式

  1. 关键词检索：通过倒排索引、BM25 等方法匹配词语，适合公司名、产品型号、错误码、合同编号等精确术语。
  2. 向量检索：将查询和文档转为向量，按语义相似度召回，适合表达不同但含义相近的内容。
  3. 元数据过滤：按时间、租户、权限、文档类型、部门或标签过滤，防止召回不应访问的数据。
  4. 混合检索：并行使用关键词和向量检索，再合并结果，兼顾精确匹配和语义匹配。
  5. 结构化查询：对于订单、财务指标等结构化数据，优先使用数据库查询或聚合，而不是只依赖向量检索。

召回流程

查询/子查询
  → 权限和元数据过滤
  → 关键词、向量或混合检索
  → 合并、去重
  → 保留候选集
  → 交给重排

召回通常取比最终上下文更多的候选，例如先取几十条，再交给重排筛选。召回过少会漏掉证据，召回过多则增加重排成本和噪声。

召回质量指标

  1. 召回率（Recall@K）表示前 K 个结果覆盖了多少相关文档；
  2. 精确率（Precision@K）表示前 K 个结果中有多少真正相关。
  3. 知识库系统还应关注不同租户、时间范围和文档类型下的召回差异。

类比：档案管理员拿着“公司名 2023 年财报、审计报告和风险提示”的检索单，在有权限的档案范围内找出 20 份可能相关的文件。此时宁可多拿一些候选，也不能因为过早筛选而漏掉关键财报。

重排

重排（Rerank）是在召回候选集之后进行的第二次排序，回答“候选内容中哪些最值得阅读和放入上下文”。它通常使用比初步召回更精确、但计算成本更高的相关性模型或业务规则。

召回与重排的区别

步骤输入目标典型特点
召回 Recall海量数据尽量不漏掉相关内容快、粗、候选多
重排 Rerank召回候选集把最相关内容排在前面慢、精、候选少

重排可以综合语义相关性、关键词命中、时间新鲜度、来源可信度、文档权限、业务优先级和去重结果。相关性分数只能作为排序依据，不能自动证明文档内容真实。

重排后的上下文组装

重排完成后不要直接把所有结果拼进 Prompt，应依次完成：

  1. 去除重复或高度相似的片段；
  2. 再次检查权限和数据范围；
  3. 保留标题、文件名、章节、页码、URL 等来源信息；
  4. 处理不同文档之间的冲突，并保留冲突来源；
  5. 按 Token 预算截取上下文；
  6. 没有足够证据时允许模型拒答或继续检索。

检索链路的完整例子

用户问题：帮我分析这家公司 2023 年的财务风险
  ↓ 意图识别：公司财务研究
  ↓ 查询改写：公司名 2023 年财报 / 审计报告 / 风险提示
  ↓ 召回：关键词 + 向量检索得到 20 份候选文档
  ↓ 重排：按相关性、时效性和来源质量留下 3～5 份
  ↓ 阅读提取：提取收入、利润、现金流和审计意见
  ↓ 上下文组装：附带来源、页码和引用
  ↓ 生成：输出有证据支持的分析

类比：项目经理先让档案管理员把 20 份可能相关的文件全部送来，这是召回；然后按相关性、年份、来源可信度和是否重复筛出最重要的 3～5 份，这是重排；最后把筛选理由和出处交给报告撰写人，而不是把整间档案室的文件全部搬进报告。

如何评估检索效果

检索质量需要拆开评估：

  • 召回层：Recall@K、Precision@K、MRR、NDCG、上下文覆盖率；
  • 生成层：答案相关性、事实忠实度、引用正确率、拒答准确率和任务成功率。

不能只看最终回答是否“像是正确的”。应建立固定问题集、标准答案或证据集，并将失败案例加入回归测试。

思维框架：Agent 如何思考与编排

“思维框架”指 Agent 组织推理、行动、检查和协作的方式。它回答的是“任务如何被拆解和推进”，不负责展开工具权限、生产监控等工程治理问题。工程安全、评估和可观测性放在本文后面的独立章节。

推理、规划和执行

  1. 推理（Reasoning）：分析当前信息，判断下一步需要什么。
  2. 规划（Planning）：把目标拆成步骤，确定顺序和完成条件。
  3. 行动（Acting）：调用工具、检索资料或执行代码。
  4. 观察（Observation）：读取行动结果，更新任务状态。
  5. 反思（Reflection）：检查结果是否满足标准，必要时修改策略。

这些能力可以组合，但不是每个任务都需要全部使用。简单问答可能只需要一次推理；查天气需要推理和一次行动；复杂研究才需要规划、循环和反思。

    A[用户目标] --> B[理解与推理]
    B --> C{需要拆解任务?}
    C -- 否 --> D[直接生成答案]
    C -- 是 --> E[制定计划]
    E --> F[执行一个步骤]
    F --> G[观察结果]
    G --> H{达到完成条件?}
    H -- 否 --> I{需要调整计划?}
    I -- 否 --> F
    I -- 是 --> E
    H -- 是 --> J[验证并交付]

CoT：链式思考

CoT（Chain-of-Thought）是一种让模型把复杂问题拆成多个中间步骤的提示策略，适合数学计算、逻辑推理、代码诊断和多步骤分析。它本身不是 Agent 架构，也不会自动提供工具或记忆。

Zero-shot CoT

请分析这道数学题，列出计算步骤，并给出最终答案：80 的 15% 是多少？

引导式 CoT

回答前检查三个问题：
1. 题目中的关键变量是什么？
2. 变量之间是什么关系？
3. 最终结果如何验证？

结构化推理结果

生产系统不应要求模型暴露完整内部思维链，也不应把 <thinking> 内容作为审计依据。更稳妥的方式是要求输出简短的步骤摘要、依据、计算过程、工具调用记录和最终结论：

{
  "steps": ["将 15% 转换为 0.15", "计算 0.15 × 80"],
  "evidence": ["用户提供的数字"],
  "answer": 12
}

ReAct：边想边做

ReAct（Reasoning + Acting）让 Agent 在“推理 → 行动 → 观察”之间循环：

用户：帮我查东京明天天气，判断是否适合跑步。
推理：需要先获取东京明天的天气。
行动：调用天气工具。
观察：18～22℃，小雨。
推理：需要根据降雨判断户外跑步是否合适。
答案：有小雨，不太适合长距离户外跑步。
sequenceDiagram
    participant U as 用户
    participant L as LLM
    participant T as 工具
    U->>L: 提交任务
    L->>L: 分析当前状态
    L->>T: 发起工具调用
    T-->>L: 返回观察结果
    L->>L: 判断继续、改计划或结束
    L-->>U: 最终答案
  1. 适合场景：搜索、工具调用、信息不完整的任务、每一步都依赖前一步结果的任务。
  2. 优点：灵活、能根据观察结果调整路径。
  3. 缺点：调用轮次和 Token 消耗较高，可能重复调用或陷入循环。

ReAct 的实现形式

经典 ReAct 让模型输出纯文本：

Thought: 我需要查询天气。
Action: search
Action Input: 东京明天天气
Observation: 东京明天 18-22℃，小雨。
Final Answer: 不太适合长距离户外跑步。

纯文本格式对程序解析不稳定。更适合工程实现的是结构化调用：

{
  "type": "tool_call",
  "tool": "search",
  "input": {"query": "东京明天天气"}
}

应用执行工具后，将结果作为工具消息写回上下文：

{
  "role": "tool",
  "name": "search",
  "content": "东京明天 18-22℃，小雨。"
}

模型随后可以继续输出 tool_call，也可以输出：

{
  "type": "final_answer",
  "answer": "东京明天有小雨，不太适合长距离户外跑步。"
}

外层程序必须设置 max_iterations、总超时和预算上限；达到边界时，应返回已有线索并说明任务未完全完成。

Plan-and-Execute：先规划再执行

Plan-and-Execute 将任务分为规划器和执行器：

用户：帮我做一个日本 7 天自由行攻略。
计划：
1. 确认城市路线
2. 查交通方式
3. 查景点开放时间
4. 安排每天行程
5. 估算预算
6. 输出表格

  1. 与 ReAct 的区别：ReAct 每一步根据观察结果即时决定下一步；Plan-and-Execute 先生成整体计划，再逐步执行。前者灵活，后者更容易控制结构和成本。

  2. 适合场景：旅行规划、报告生成、竞品分析、项目型任务和多阶段执行。

计划不是不可修改的脚本。执行过程中遇到事实变化、工具失败或约束变化时，应回到规划阶段；每个子任务应有输入、输出、完成条件和失败处理。

Reflexion：执行后反思

Reflexion 的流程是：执行任务 → 评估结果 → 找出问题 → 调整策略 → 再执行。它适合写作优化、代码调试、长任务迭代和需要质量提升的任务。

第一版销售邮件：开头生硬、没有体现客户痛点、CTA 不明确。
反思结果：补充客户场景，调整语气，增加明确行动按钮。
第二版：根据反思结果重新生成并再次检查。

反思必须有明确的评价标准，例如 Schema 校验、引用覆盖、单元测试、事实一致性或业务规则；只让模型说“请检查一下”通常不能稳定提升质量。反思可以由同一模型完成，也可以由独立 Critic 完成。

Human-in-the-Loop：人在关键节点介入

Human-in-the-Loop 不是一种推理算法，而是一种控制模式。Agent 在高风险或低置信度节点暂停，由人确认后继续：

Agent 草拟邮件 → 用户确认 → Agent 发送
Agent 推荐投资方案 → 用户确认 → 不自动下单
Agent 生成删除计划 → 用户确认 → 再删除文件

适合发邮件、支付、删除数据、法律/医疗/金融和生产环境变更。人工介入应有明确的待确认内容、超时处理、拒绝分支和审计记录。

Critic / Reviewer：生成与审查

一个 Agent 负责生成，另一个 Agent 负责审查：

Generator 生成答案
  ↓
Critic 按规则检查事实、格式和风险
  ↓
通过 → 交付
不通过 → 返回 Generator 修改

审查结果应包含具体问题、证据和修改建议，不能只返回“好/不好”。应设置最大审查轮次，避免生成器和审查器互相循环。

Debate / Multi-Agent Debate：多方辩论

多个 Agent 扮演不同角色，相互挑战观点，再由裁判汇总：

Agent A：提出方案
Agent B：提出反对意见
Agent C：检查证据和风险
Agent D：根据评价标准裁决

适合策略评审、风险识别、论文或代码审查。它不能自动保证结论正确，参与者使用相同错误资料时可能形成“集体确认偏差”，因此仍需要外部证据和明确评价标准。

Multi-Agent：任务分工协作

Multi-Agent 是系统组织方式，不是单独的推理算法。可以让规划 Agent、检索 Agent、执行 Agent 和审查 Agent 分工，但需要明确：

  • 每个 Agent 的职责和输入输出协议；
  • 共享哪些状态，如何避免并发覆盖；
  • 子任务失败时由谁重试、降级或接管；
  • 何时并行，何时必须串行；
  • 最终由哪个 Agent 汇总和交付。

只有当任务可以自然拆分、需要独立专业能力或能够并行执行时，Multi-Agent 才值得引入。单 Agent + Workflow 往往更容易调试。

Router / 专家路由（MRKL，了解即可）

MRKL 是早期“专家模块 + 模型路由”的架构思想：先判断问题类型，再交给聊天模型、搜索、计算器、天气 API 或数据库等专门模块。它有助于理解今天的 Router、意图分类、Workflow 条件分支和工具选择，但不需要单独学习某个 MRKL 框架或实现。

数学问题 → 计算器
天气问题 → 天气 API
搜索问题 → 搜索引擎
数据问题 → 数据库
普通聊天 → LLM

工程实践中应重点掌握路由的输入输出、低置信度兜底和未知意图处理，而不是记忆 MRKL 这个名称。路由错误时，应允许澄清或转人工，不能强行调用错误工具。

各种模式如何组合

这些模式可以分层组合：

flowchart TD
    A[用户目标] --> B[MRKL 路由]
    B --> C[Plan-and-Execute 制定计划]
    C --> D[ReAct 执行子任务]
    D --> E[工具或 RAG]
    E --> F[Critic 检查结果]
    F -->|不通过| G[Reflexion 调整策略]
    G --> D
    F -->|通过| H{是否高风险?}
    H -->|是| I[Human-in-the-Loop 确认]
    H -->|否| J[交付结果]
    I --> J

一个完整系统可以使用 MRKL 选择领域，使用 Plan-and-Execute 拆解任务，在每个子任务中使用 ReAct 调工具，使用 Critic/Reflexion 提升质量，在高风险动作前引入人工确认。选择模式时优先考虑任务的确定性、可解释性、延迟、成本和失败后果。

模式选择决策表

场景优先模式原因
一次性复杂推理CoT/结构化推理不需要外部行动
多步搜索或工具调用ReAct每一步依赖观察结果
可拆解的长任务Plan-and-Execute计划和进度更清晰
需要多轮质量提升Reflexion/Critic有明确评价标准
多领域工具选择MRKL/Router先决定交给哪个专家
角色明确且可并行Multi-Agent分工或并行带来收益
付款、删除、发布Human-in-the-Loop需要人承担最终责任

学习优先级

这些名称并不属于同一层次，不能把它们都当成需要安装和使用的框架：

层次内容在学习路线中的作用
推理策略CoT、结构化推理让模型更有条理地分析问题
执行循环ReAct、Agent Loop连接推理、工具和观察结果
任务编排Workflow、Plan-and-Execute控制步骤、状态和任务进度
路由思想MRKL、Router将问题交给合适的专家或工具
质量改进Critic、Reflexion、Debate检查和修正结果
协作架构Multi-Agent让多个专业角色分工协作
风险控制Human-in-the-Loop在关键动作前引入人工确认
历史实践AutoGPT了解早期自主 Agent 的探索和局限

为了减少学习成本，可以按下面的顺序掌握：

  1. 优先掌握：Agent Loop、Tool Calling、ReAct、Workflow、Plan-and-Execute、Human-in-the-Loop。这些概念直接对应当前 Agent 应用中的执行、编排和风险控制。
  2. 随后掌握：RAG 路由、Critic/Reviewer、Reflexion、Multi-Agent。它们用于提升检索质量、结果质量或处理复杂协作任务，应在单 Agent 流程稳定后再引入。
  3. 了解概念即可：MRKL、AutoGPT 等名称更多用于理解 Agent 的演进和架构思想。AutoGPT 早期强调完全自主的目标驱动循环，容易出现重复执行、成本失控和难以调试的问题，因此不作为本文的主线实践框架。

MRKL 在本文中保留的是“路由到专家模块”的思想，不要求学习某个具体框架；工程上通常以 Router、分类器、Workflow 条件边或模型工具选择来实现。

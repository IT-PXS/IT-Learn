SpringAi（3-会话记忆）

爱编程的小生2025/12/3大约 17 分钟JavaSpringAiAi

版本、依赖及配置

本文示例以 Spring AI 1.1.2 为基准，对应的 Spring Boot 版本使用 3.5.8，JDK 使用 17：

JDK 17 + Spring Boot 3.5.8 + Spring AI 1.1.2

Spring AI、Spring Boot 和 JDK 需要使用兼容的版本组合。本文沿用上一篇的 BOM 和 spring-ai-starter-model-openai 依赖，不再重复基础 Maven 配置；JDBC 和向量记忆需要补充对应的模块。

以下配置示例是不同方案的替代写法，不要把多个同名的 chatMemory、chatClient Bean 一起复制到同一个项目中。示例省略 import，依赖版本由 Spring AI BOM 和 Spring Boot 依赖管理统一提供。

模型配置沿用上一篇文章的 OpenAI 兼容接口示例：

spring:
  ai:
    openai:
      base-url: https://dashscope.aliyuncs.com/compatible-mode
      api-key: ${DASHSCOPE_API_KEY}
      chat:
        options:
          model: qwen3-max
          temperature: 0.75

会话记忆依赖的是消息管理能力，不会改变底层聊天模型的配置。

会话记忆的基本原理

为什么普通调用没有上下文

@Resource
private ChatModel chatModel;

@GetMapping("/chat")
public String chat() {
    String answer = chatModel.call("你好，我是 Java 工程师");
    System.out.println(answer);

    String answer2 = chatModel.call("我是谁");
    System.out.println(answer2);
    return "success";
}

第一次调用和第二次调用分别执行了 chatModel.call(String)，第二次调用没有携带第一轮消息，因此模型无法根据上一轮对话确定“我”指的是谁。即使模型猜出了某个身份，也不代表它读取了上一轮消息。普通聊天调用是无状态的：模型不会因为使用了同一个 ChatModel 就自动保存历史消息。

手动保存和拼接历史消息

让 AI 具备上下文的基本方式，是由应用保存历史消息，并在下一次请求中把历史消息和当前问题一起放入 Prompt。下面使用 conversationId 区分不同会话：

@RestController
public class ChatMemoryController {

    // 每个 conversationId 对应一份独立的历史消息
    private final Map<String, List<Message>> histories = new ConcurrentHashMap<>();

    // 每个会话最多保留的消息数量
    private static final int MAX_LEN = 10;

    @Resource
    private ChatClient chatClient;

    @RequestMapping(value = "/demo", produces = "text/html;charset=UTF-8")
    public String chat(@RequestParam("conversationId") String conversationId,
                       @RequestParam("msg") String msg) {
        List<Message> history = histories.computeIfAbsent(
                conversationId, id -> new ArrayList<>());

        synchronized (history) {
            // 先构造本次请求，调用成功后再提交到历史列表
            List<Message> requestMessages = new ArrayList<>(history);
            requestMessages.add(new UserMessage(msg));

            // 控制上下文长度，超出后移除最早的消息
            while (requestMessages.size() > MAX_LEN) {
                requestMessages.remove(0);
            }

            ChatResponse response = chatClient.prompt(new Prompt(requestMessages))
                    .call()
                    .chatResponse();
            AssistantMessage assistantMessage = response.getResult().getOutput();

            // 保存本轮助手回复，供下一次请求使用
            requestMessages.add(assistantMessage);
            while (requestMessages.size() > MAX_LEN) {
                requestMessages.remove(0);
            }
            history.clear();
            history.addAll(requestMessages);
            return assistantMessage.getText();
        }
    }
}

这个示例只用于说明会话记忆的原理。历史消息保存在当前应用进程的内存中，应用重启后会丢失；实际项目可以使用 Spring AI 提供的 ChatMemory 和 ChatMemoryRepository。

示例使用的 ChatClient 不应再注册记忆 Advisor，否则手动提交的历史可能被重复加入。synchronized 只保证当前实例内同一个会话的请求串行执行；还需要按业务设置会话过期和清理机制，避免 Map 一直增长。

conversationId 只是会话标识，不等于权限校验。应用仍然需要确认当前用户有权访问这个会话。

ChatMemory

大型语言模型本身不会保存不同请求之间的消息。Spring AI 的 ChatMemory 用于管理多轮对话中需要再次提供给模型的消息。

会话记忆和完整聊天记录的用途不同：前者服务于本次模型调用，允许丢弃较早的消息；后者用于页面展示、审计或回放，通常需要保留全部消息。即使把记忆保存到数据库，也不代表获得了一份完整聊天记录。

ChatMemory 和 ChatMemoryRepository 的职责

ChatMemory 和 ChatMemoryRepository 分工不同：

类型职责
ChatMemory管理会话消息，决定读取哪些消息以及何时淘汰消息
ChatMemoryRepository按会话 ID 保存、读取和删除消息

ChatMemoryRepository 只负责底层存储，不负责决定窗口大小、消息淘汰或 Prompt 如何组装。saveAll() 用传入的消息集合替换指定会话中已有的消息，不是简单追加。

常见的 Repository 实现包括：

  • InMemoryChatMemoryRepository：消息保存在当前应用进程内，重启后丢失。
  • JdbcChatMemoryRepository：使用关系数据库保存消息，适合跨重启和多实例共享。
  • CassandraChatMemoryRepository：使用 Cassandra 保存消息，适合分布式和大规模场景。
  • Neo4jChatMemoryRepository：使用 Neo4j 保存消息及其关系。
  • MongoChatMemoryRepository：使用 MongoDB 保存消息。
  • CosmosDBChatMemoryRepository：使用 Azure Cosmos DB 保存消息。

更换 Repository 只改变消息的存储位置，不会自动改变 ChatMemory 的保留策略。例如，使用 JDBC Repository 仍然可以通过 MessageWindowChatMemory 只保留最近 10 条消息。

接口结构

下面保留两个接口的主要结构，帮助理解 Spring AI 如何划分会话管理和底层存储职责。

ChatMemory 负责面向会话管理消息：

public interface ChatMemory {

    // 未指定会话 ID 时使用的默认值
    String DEFAULT_CONVERSATION_ID = "default";

    // Advisor 从上下文中读取会话 ID 时使用的参数键
    String CONVERSATION_ID = "chat_memory_conversation_id";

    // 添加一条消息
    default void add(String conversationId, Message message) {
        Assert.hasText(conversationId, "conversationId cannot be null or empty");
        Assert.notNull(message, "message cannot be null");
        this.add(conversationId, List.of(message));
    }

    // 添加多条消息
    void add(String conversationId, List<Message> messages);

    // 获取当前会话保留的消息
    List<Message> get(String conversationId);

    // 清空当前会话
    void clear(String conversationId);
}

ChatMemoryRepository 面向底层存储：

public interface ChatMemoryRepository {

    // 查询已有的会话 ID
    List<String> findConversationIds();

    // 查询某个会话的消息
    List<Message> findByConversationId(String conversationId);

    // 用新的消息集合替换该会话的已有消息
    void saveAll(String conversationId, List<Message> messages);

    // 删除某个会话的全部消息
    void deleteByConversationId(String conversationId);
}

接口中的 saveAll() 表明 Repository 接收的是一份完整消息集合。窗口策略由 ChatMemory 决定，Repository 只负责保存这份结果。

基本操作

每条记忆都属于一个 conversationId。同一个 ID 读取同一份上下文，不同 ID 的消息互相隔离：

String conversationId = "user-1001-session-01";

// 保存消息
chatMemory.add(conversationId, new UserMessage("你好"));

// 获取当前会话保留的消息
List<Message> messages = chatMemory.get(conversationId);

// 清空当前会话
chatMemory.clear(conversationId);

ChatMemory 决定“保留哪些消息”，ChatMemoryRepository 负责“把这些消息存在哪里”。

消息窗口

MessageWindowChatMemory 是 Spring AI 1.1.2 内置的记忆实现，默认最多保留 20 条消息，可以通过 maxMessages() 调整。超出窗口后，会淘汰较早的消息。

这里限制的是消息条数，不是对话轮数，也不是 Token 数量。一次普通问答通常包含一条 UserMessage 和一条 AssistantMessage，因此 10 条消息大致对应 5 轮完整问答。消息内容很长时，即使条数没有超限，也可能超过模型的上下文长度，需要额外控制输入长度或采用摘要策略。

System 消息有特殊规则：加入新的 System 消息时会替换已有的 System 消息；淘汰消息时优先保留 System 消息。本文通过 defaultSystem() 提供系统指令，不需要每轮再手动保存一次。

ChatMemory Advisor

记忆 Advisor 属于 ChatClient 的 Advisor 调用链。它们通常会在请求前读取历史消息、在请求中注入上下文，并在响应后保存新的消息。

Advisor处理方式适用场景
MessageChatMemoryAdvisor按原来的 Message 类型加入历史消息希望保留 User、Assistant 等消息角色
PromptChatMemoryAdvisor将历史消息整理成文本并追加到 System Prompt希望控制历史记忆的展示格式
VectorStoreChatMemoryAdvisor从向量库检索与当前问题相关的历史长对话或长期记忆场景

通常选择一种记忆 Advisor 即可，不要同时把同一份记忆注册到多个 Advisor 中。

普通多轮对话优先使用 MessageChatMemoryAdvisor。在 1.1.2 中，它会先读取历史并加入 Prompt，再保存当前用户消息；响应返回后保存助手消息。流式调用会聚合响应后再保存助手消息。请求失败或流被中断时，可能只留下用户消息，业务需要自行决定如何处理失败轮次。

记忆 Advisor 不会自动保存工具调用过程中的全部中间消息，也不能作为完整审计日志使用。

Advisor 会自动完成消息保存，调用时只传入当前用户问题，不要再手动 add() 同一条消息或把同一份历史放入 Prompt，否则可能产生重复记录。

内存会话记忆

内存存储适合学习和本地调试。应用重启后消息会丢失，多实例部署时不同实例之间也不会共享记忆。

依赖配置

沿用上一篇的 OpenAI Starter 即可使用内存记忆：

<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>

在 1.1.2 中，这个 Starter 已经传递引入 spring-ai-autoconfigure-model-chat-memory。因此不需要再添加一个独立的内存 Chat Memory Starter。

自动配置的内存 ChatMemory

如果应用没有定义 ChatMemoryRepository，自动配置会提供 InMemoryChatMemoryRepository；如果没有定义 ChatMemory，会基于当前 Repository 创建 MessageWindowChatMemory：

ChatMemory
  → MessageWindowChatMemory：控制每个会话保留哪些消息
  → InMemoryChatMemoryRepository：把消息保存在当前应用进程内

手动使用 ChatMemory

直接使用 ChatMemory 时，需要自己完成“读取历史 → 组装 Prompt → 保存回复”：

@RestController
public class ManualMemoryController {

    @Resource
    private ChatMemory chatMemory;
    @Resource
    private ChatModel chatModel;

    @GetMapping("/chat-memory/manual")
    public String chat(@RequestParam("msg") String msg,
                       @RequestParam("conversationId") String conversationId) {
        chatMemory.add(conversationId, new UserMessage(msg));

        Prompt prompt = new Prompt(chatMemory.get(conversationId));
        ChatResponse response = chatModel.call(prompt);
        AssistantMessage answer = response.getResult().getOutput();

        chatMemory.add(conversationId, answer);
        return answer.getText();
    }
}

这个例子适合说明 ChatMemory 的工作步骤。使用流式响应时，应该在流结束后聚合完整的助手回复再保存，不能把每个响应片段分别保存成一条消息。

add → get → call → add 是多个独立操作，不能保证同一个会话的并发请求按顺序完成。学习时可以串行发送请求；实际项目应按会话串行处理或设计并发控制，数据库存储也不会自动解决整个调用过程的竞争问题。

使用 MessageChatMemoryAdvisor

下面显式创建一个最多保留 10 条消息的内存窗口：

@Configuration
public class MemoryConfiguration {

    @Bean
    public ChatMemory chatMemory() {
        return MessageWindowChatMemory.builder()
                // 消息只保存在当前应用进程内，重启后会丢失
                .chatMemoryRepository(new InMemoryChatMemoryRepository())
                // 每个会话最多保留 10 条消息
                .maxMessages(10)
                .build();
    }

    @Bean
    public ChatClient chatClient(ChatModel chatModel, ChatMemory chatMemory) {
        return ChatClient.builder(chatModel)
                .defaultSystem("你是一名 Java 技术助手，回答要简洁。")
                .defaultAdvisors(
                        MessageChatMemoryAdvisor.builder(chatMemory).build(),
                        new SimpleLoggerAdvisor())
                .build();
    }
}

请求时通过 ChatMemory.CONVERSATION_ID 指定会话：

@RestController
public class MemoryController {

    @Resource
    private ChatClient chatClient;

    @GetMapping(value = "/chat-memory", produces = "text/html;charset=UTF-8")
    public String chat(@RequestParam("msg") String msg,
                       @RequestParam("conversationId") String conversationId) {
        return chatClient.prompt()
                .user(msg)
                // 记忆 Advisor 根据这个 ID 读取和保存对应会话
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
                .call()
                .content();
    }
}

同一个 conversationId 会连续使用同一份上下文；使用一个尚未出现过的 ID，会创建独立的新会话。在 1.1.2 中，省略该参数会使用默认的 default 会话，所以多会话应用应在每次请求中显式传入 ID。

可以顺序调用接口验证效果：

conversationId=session-01，msg=我叫小板
conversationId=session-01，msg=我叫什么名字？
conversationId=session-02，msg=我叫什么名字？

第二次调用应能利用第一轮信息；第三次调用不应获得 session-01 的历史。还可以在 chatMemory.clear("session-01") 后重新提问，检查记忆是否已经清空。

上面使用同步调用，便于观察完整回复。如果需要逐段展示，可以把返回值改为 Flux<String>，并使用 stream().content()。流式模型调用需要 Reactive HTTP 客户端支持，可在现有 Web 依赖之外增加 spring-boot-starter-webflux；记忆配置和会话参数保持一致。

使用 PromptChatMemoryAdvisor

本节展示 1.1.2 的 API。PromptChatMemoryAdvisor 自 1.1.3 起被弃用，后续版本的模板行为也有变化；新项目优先选择 MessageChatMemoryAdvisor，升级时应检查对应版本的迁移说明。

PromptChatMemoryAdvisor 也使用 ChatMemory，但它不会把历史消息原样加入 Prompt，而是把用户消息和助手消息整理成文本，再追加到 System Prompt 中。

可以通过 PromptTemplate 自定义历史记忆的格式：

@Bean
public PromptChatMemoryAdvisor promptChatMemoryAdvisor(ChatMemory chatMemory) {
    PromptTemplate template = new PromptTemplate("""
            {instructions}

            请结合 MEMORY 中的历史对话回答当前问题。
            ---------------------
            MEMORY:
            {memory}
            ---------------------
            """);

    return PromptChatMemoryAdvisor.builder(chatMemory)
            .systemPromptTemplate(template)
            .build();
}

模板中的 {instructions} 会替换为原来的系统指令，{memory} 会替换为当前会话的历史文本。注册方式与 MessageChatMemoryAdvisor 相同，但通常二选一，不要把同一份 ChatMemory 同时注册到两个 Advisor。

@Bean
public ChatClient chatClient(ChatModel chatModel,
                             PromptChatMemoryAdvisor memoryAdvisor) {
    return ChatClient.builder(chatModel)
            .defaultSystem("你是一名 Java 技术助手，回答要简洁。")
            .defaultAdvisors(memoryAdvisor, new SimpleLoggerAdvisor())
            .build();
}

数据库会话记忆

当记忆需要跨应用重启保存，或需要被多个应用实例共享时，可以把 ChatMemoryRepository 换成数据库实现。ChatMemory 仍然负责消息窗口，Repository 只负责持久化消息。

JDBC（MySQL）

Spring AI 1.1.2 提供 JDBC Chat Memory Repository。Spring AI 模块的版本由 Spring AI BOM 管理，MySQL 驱动版本由 Spring Boot 管理；这里使用 JDBC，不需要引入 MyBatis-Plus：

<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-chat-memory-repository-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>

数据源和 Schema 初始化配置如下：

把下面的配置合并到前面的 application.yml 中，保留模型配置，不要在同一个 YAML 文件中重复定义顶层 spring 键。

spring:
  ai:
    chat:
      memory:
        repository:
          jdbc:
            # 开发环境执行初始化脚本；生产环境由迁移工具管理表结构
            initialize-schema: always

  datasource:
    url: jdbc:mysql://localhost:3306/springai?serverTimezone=Asia/Shanghai
    username: root
    password: your-password

initialize-schema 有三个常用值：

  • embedded：只对内嵌数据库初始化。
  • always：每次启动时执行初始化脚本，不代表自动升级已有表结构。
  • never：不执行初始化脚本。

生产环境通常先执行官方 Schema 脚本，再设置为 never，避免应用启动时隐式修改数据库结构。脚本位置和数据库平台可以通过 schema、platform 属性覆盖。

先创建数据源 URL 中的 springai 数据库，初始化脚本只负责创建表，不会创建数据库。1.1.2 默认 MySQL 表中的 conversation_id 长度是 36，建议使用 UUID 等符合长度要求的标识；该版本按 timestamp 排序，默认 MySQL 时间戳精度为秒，同一秒写入的消息可能存在顺序不稳定的问题。对顺序有严格要求时，需要核实并调整存储实现或评估升级。

配置 JDBC Repository 后，将它注入 MessageWindowChatMemory：

@Configuration
public class JdbcMemoryConfiguration {

    @Bean
    public ChatMemory chatMemory(JdbcChatMemoryRepository repository) {
        return MessageWindowChatMemory.builder()
                .chatMemoryRepository(repository)
                .maxMessages(10)
                .build();
    }

    @Bean
    public ChatClient chatClient(ChatModel chatModel, ChatMemory chatMemory) {
        return ChatClient.builder(chatModel)
                .defaultSystem("你是一名 Java 技术助手。")
                .defaultAdvisors(
                        MessageChatMemoryAdvisor.builder(chatMemory).build(),
                        new SimpleLoggerAdvisor())
                .build();
    }
}

请求时仍然要传入 ChatMemory.CONVERSATION_ID：

return chatClient.prompt()
        .user(msg)
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
        .stream()
        .content();

Redis

Spring AI 1.1.2 没有内置 Redis ChatMemoryRepository。如果选择 Redis，需要自己实现接口，并明确消息的序列化格式：

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>

一个会话可以使用一个 Redis List，键名例如 spring-ai:chat-memory:{conversationId}：

  • saveAll 先删除旧 List，再按消息顺序写入完整列表；
  • findByConversationId 按相同顺序读取并反序列化；
  • deleteByConversationId 直接删除这个 List；
  • findConversationIds 扫描此前缀开头的键。

示例只展示存储结构。MessageCodec 是本文为了隐藏序列化细节定义的示意接口，不属于 Spring AI API，需要由应用根据实际使用的消息类型实现：

public final class RedisChatMemoryRepository implements ChatMemoryRepository {

    private static final String KEY_PREFIX = "spring-ai:chat-memory:";
    private final StringRedisTemplate redisTemplate;
    private final MessageCodec messageCodec;

    public RedisChatMemoryRepository(StringRedisTemplate redisTemplate,
                                     MessageCodec messageCodec) {
        this.redisTemplate = redisTemplate;
        this.messageCodec = messageCodec;
    }

    @Override
    public List<Message> findByConversationId(String conversationId) {
        List<String> values = redisTemplate.opsForList()
                .range(KEY_PREFIX + conversationId, 0, -1);
        return values == null ? List.of()
                : values.stream().map(messageCodec::decode).toList();
    }

    @Override
    public void saveAll(String conversationId, List<Message> messages) {
        String key = KEY_PREFIX + conversationId;
        redisTemplate.delete(key);
        if (!messages.isEmpty()) {
            redisTemplate.opsForList().rightPushAll(
                    key, messages.stream().map(messageCodec::encode).toList());
        }
    }

    @Override
    public void deleteByConversationId(String conversationId) {
        redisTemplate.delete(KEY_PREFIX + conversationId);
    }

    @Override
    public List<String> findConversationIds() {
        Set<String> keys = redisTemplate.keys(KEY_PREFIX + "*");
        return keys == null ? List.of()
                : keys.stream().map(key -> key.substring(KEY_PREFIX.length())).toList();
    }
}

这里使用 StringRedisTemplate，确保键和值按字符串序列化。MessageCodec 至少需要保存消息角色和文本；如果使用工具调用、多模态或元数据，还需要明确这些字段的编码方式。

示例中的“删除旧列表 → 写入新列表”不是原子操作，失败时可能丢失旧数据，读取时也可能看到空列表。生产环境应使用 Lua 脚本或事务完成原子替换；整个记忆的读改写过程仍需单独处理同会话并发。KEYS 适合小规模演示，生产环境应使用 SCAN，并设置会话过期策略。

实现 Repository 后，还需要把它注册为 Bean，并注入 MessageWindowChatMemory，再按前面的方式配置 Advisor。不要继续使用显式创建 InMemoryChatMemoryRepository 的配置，否则消息仍然会保存在内存中。

例如，先定义编码接口，并由业务提供它的实现 Bean：

public interface MessageCodec {
    String encode(Message message);
    Message decode(String value);
}

再配置 Repository 和记忆窗口：

@Bean
public ChatMemoryRepository redisChatMemoryRepository(
        StringRedisTemplate redisTemplate, MessageCodec messageCodec) {
    return new RedisChatMemoryRepository(redisTemplate, messageCodec);
}

@Bean
public ChatMemory chatMemory(ChatMemoryRepository repository) {
    return MessageWindowChatMemory.builder()
            .chatMemoryRepository(repository)
            .maxMessages(10)
            .build();
}

MessageCodec 的具体实现和 Redis 连接配置仍需补齐，这部分是自定义扩展示例，不是可以直接运行的完整工程。

向量会话记忆

工作原理

向量记忆适合历史消息较多、希望按语义找回相关内容的场景。VectorStoreChatMemoryAdvisor 会把 User 和 Assistant 消息写入 VectorStore，并在每次请求前使用当前问题进行相似度搜索；搜索条件还会包含 conversationId，因此不同会话的消息不会混在一起。检索结果随后会作为文本追加到 System Prompt 中。

它与 MessageChatMemoryAdvisor 的区别是：前者按语义检索相关历史，后者按消息窗口保留最近消息。向量记忆需要 EmbeddingModel 和具体的 VectorStore 实现，不能只引入聊天模型依赖。使用哪种向量数据库，就引入对应的 Vector Store Starter，并完成该数据库的连接配置。

这个 Advisor 直接操作 VectorStore，不经过 ChatMemory 和 ChatMemoryRepository，也不受 maxMessages() 限制。还需要引入 1.1.2 对应的 Advisor 模块：

<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-advisors-vector-store</artifactId>
</dependency>

VectorStoreChatMemoryAdvisor 位于 org.springframework.ai.chat.client.advisor.vectorstore 包。下面代码假设已经配置好可用的 VectorStore Bean；仅复制 Advisor 配置还不能完成向量存储初始化。

ChatClient 配置与调用

@Bean
public VectorStoreChatMemoryAdvisor vectorStoreChatMemoryAdvisor(VectorStore vectorStore) {
    return VectorStoreChatMemoryAdvisor.builder(vectorStore)
            .defaultTopK(20)
            .build();
}

@Bean
public ChatClient chatClient(ChatModel chatModel,
                             VectorStoreChatMemoryAdvisor memoryAdvisor) {
    return ChatClient.builder(chatModel)
            .defaultAdvisors(memoryAdvisor, new SimpleLoggerAdvisor())
            .build();
}

调用时仍需传入会话 ID；还可以按请求覆盖检索条数：

return chatClient.prompt()
        .user(msg)
        .advisors(a -> a
                .param(ChatMemory.CONVERSATION_ID, conversationId)
                .param(VectorStoreChatMemoryAdvisor.TOP_K, 5))
        .stream()
        .content();

向量存储不是普通消息的完整备份。它只保存可转换为文本向量的 User、Assistant 消息，检索结果也不保证按时间顺序完整还原整个会话；如果业务需要完整审计或精确回放，应在独立的业务消息存储中保留完整记录。

topK 限制的是检索文档条数，不是对话轮数。单独使用向量记忆时，最近一轮消息也可能没有被检索出来，不能保证与消息窗口相同的连续对话效果。1.1.2 会把会话 ID 拼入检索过滤表达式，建议由服务端生成并限制为 UUID 等格式。清除 ChatMemory 不会删除向量库中的历史，需要另外按会话元数据删除对应文档。

会话记忆方案选择

方案主要特点适用场景
内存存储配置简单，应用重启后丢失学习、本地调试
数据库存储持久化当前记忆窗口，可跨重启和多实例共享需要持久化上下文的应用
Redis 存储读写速度快，需要自行实现 Repository高并发、已有 Redis 基础设施
向量存储按语义检索相关历史，不保证完整还原会话长对话、长期记忆

如果业务需要完整聊天记录，应在记忆窗口之外设计独立的消息表或日志，不要依赖 MessageWindowChatMemory 保存全部历史。如果业务更关注从长期历史中找回相关信息，可以增加向量存储；组合使用时需要明确各自的写入、检索和删除规则，避免重复注入上下文。
